# Workflow 设计经验

与 `workflow-json` 设计 SKILL 配合使用。设计 SKILL 定义可执行的节点、端口、类型和进程语义；本 SKILL 提供结构选择与优化方法。假设 agent 只有这两份 SKILL 和用户输入，没有仓库、示例文件或可用运行时。可读取文件时，设计 SKILL 位于 [../workflow-json/SKILL.md](../workflow-json/SKILL.md)；也可直接使用用户提供的同名全文。

遵循设计 SKILL 的输出格式。以下流程片段是结构示意，生成最终 JSON 时必须展开为已支持的真实节点和连线。经验不增加节点、参数、共享函数库或运行时能力；不能从中推断工具已注册。缺少基础设计 SKILL 时，先取得它再生成可执行 JSON。

## 先确定状态，再确定结构

对重要数据判断：谁创建、谁修改、被谁读取、跨越哪些生命周期、何时失效。无需为简单任务额外输出分析表。

| 使用方式 | 优先表达 | 判断依据 |
|---|---|---|
| 同一次调用中的临时结果 | 普通数据端口 | 来源位于合法的同级或祖先作用域，无需共享更新 |
| 进入函数、从函数返回的数据 | 明确的函数输入和输出 | 函数内部节点不能直接连到调用方 |
| 当前函数在终端等待后继续使用的局部值 | 当前执行帧中的节点输出 | 正常阻塞与恢复会保存帧；等待本身不要求新增 Context |
| 跨轮次的历史、循环聚合结果、多个调用共享的可变状态 | Context，并显式传递 ID | 需要读写共享值或越过合法数据流的生命周期边界 |
| 一次批次中的共享标志 | 批次开始时初始化的 Context | 下一批必须重新初始化，避免沿用旧决定 |
| 独立执行、具有独立终端和进程生命周期的工作 | 真实子流程 | 必须已有明确的文件依赖和接口 |

优先显式传递 Context ID，减少对固定 ID 的隐含依赖。不要为了缓存任意中间值建立 Context，也不要用 Session 代替未分析清楚的状态生命周期。正常等待恢复不等于任意崩溃恢复或外部副作用恰好执行一次。

## 控制结构的选择

- 单次任务先用直线流程；有限列表处理用 `foreach`。只有需要动态决定后续任务时，才考虑 Context 队列与 `while_pop`。停止条件必须能从用户需求和实际分支解释清楚。
- 当前控制流不允许普通分支合流。每条分支独立结束；需要向调用方返回统一结果时，放进本地函数，由各分支自己的 `function_output` 返回。不要把两个分支都接到一个收尾节点。
- 循环体需要 Router、JSON Tool 成功/失败分支或其他多出口节点时，把一次迭代放进本地函数，循环体只保留一个 `function_call`。函数各分支返回调用方后，再由调用方回到循环。
- 以函数处理复用和局部分支。仅为了画布分组而创建子进程，会引入额外接口、终端和失败传播语义。

按任务采用结构，不必为所有 workflow 添加模型循环、人类等待或队列。对于需要自动工具循环的任务，可使用：

```text
初始化历史与待执行轮次队列
→ while_pop
    loop-out → function_call(执行一轮) → loop-in
    control-out → output

执行一轮：
读取历史 → LLM → 保存 assistant → 判断是否有工具调用
  无：输出最终结果 → 本分支返回
  有：foreach(调用执行单个工具的函数) → 将下一轮加入队列 → 本分支返回
```

函数名仅为语义示意，需要在当前 JSON 的 `metadata.functions` 中声明并实现。示例结构不自带轮次上限；按用户需求设计终止或预算策略，不能把运行时执行超时解释为合理的业务终止条件。

## 优先消除表示和转换成本

优化顺序通常是：直接连接兼容端口 → 使用已有转换节点 → 提取重复结构 → 必要时提出能力扩展。减少节点不能改变状态更新顺序、错误处理或等待语义。

| 发现的结构 | 可以考虑的替换 | 适用条件 |
|---|---|---|
| 数字 → 构造单字段 Struct → JSON → 反序列化取文本 | `number_to_content` | 仅需数字的 JSON 文本表示 |
| 为 assistant 有无 tool call 分别构造消息 | 一个 `construct_message(role=assistant)` | 连接 content、reasoning、工具调用的真实端口 |
| 逐项解析调用并用 Context 拼对象列表，只为构造 assistant 消息 | 将 LLM 的调用列表直接接入消息节点 | 单个调用执行时需要解析的部分仍保留 |
| 每次提问都把全部终端历史交回模型 | 提问前 `list_length`，恢复后 `list_slice` | 终端输入按时间追加；只需要本次新增回复 |
| 只调用一次、只包装一个普通节点的函数 | 内联该节点 | 没有必要的生命周期边界或稳定接口价值 |

例如只判断调用数是否为零时，可以用 `list_length → number_to_content → router`，无需为计数声明 Struct。但包含真实业务字段的 Struct 仍用于结构校验，不应一概删除。

## 消息和工具执行的固定约束

对使用设计 SKILL 所述 Chat Completions 消息协议的流程：

- 历史列表保存 JSON 编码的消息文本。assistant 统一由 `construct_message` 构造；LLM 的 `tool_calls:list-content` 接 `tool-calls-in`，由节点转为对象数组。不能把调用对象数组再次序列化为字符串数组写进消息。
- `reasoning-in` 的提供不应取决于调用数。无调用时仍保留已提供的 reasoning。LLM 的 content 可能缺失，按设计 SKILL 用 `construct_content` 等已有能力规范为字符串后再构造消息。
- 先保存 assistant 的调用记录，再执行调用、记录结果。成功、失败、拒绝、跳过等结果都使用原调用 ID，经 `construct_message(role=tool)` 的 `tool-call-id-in` 写入。
- 下一次请求模型前，为已记录的每个工具调用补齐对应结果。取消或跳过剩余批次时，应写明原因并保留 ID 对应关系；不要静默丢弃这些调用后直接开始下一轮。
- `json_tool` 的成功、失败分支分别生成结果并返回；不要从成功分支读取错误数据，或从错误分支读取成功数据。工具错误转为观察后，是否重试或继续由任务政策决定，不能自动套用无限重试。

将“记录工具结果”集中为一个本地函数通常有价值：输入历史 ID、调用 ID、结果文本，构造 tool 消息并追加历史。不要通过放松通用 Struct 校验来容纳供应商协议差异；协议规范化属于明确的适配边界。

## 人类交互作为可选工具

当需求允许模型主动提问时，可向模型提供提问工具定义，并在 workflow 内部路由该调用。向模型声明工具和实际执行工具是两件事；不要虚构一个已注册的同名外部 Tool。

推荐的交互片段：

```text
解析本次问题
→ read_terminal_input → list_length（保存提问前长度）
→ 输出问题 → wait_terminal_event
→ read_terminal_input
→ list_slice(start=提问前长度)
→ 将所有新增回复编码为结果 → 记录原调用 ID 的 tool 消息
```

- 保存游标应早于显示问题，避免把提示后到达的输入当成旧历史。恢复后必须显式读取；等待节点本身不返回消息。
- 保留切片内所有回复及顺序，不默认只取最后一条。需要 JSON 包装时可用已声明 Struct 与 `struct_to_json`，不要手工拼接用户文本。
- 当前等待只由进程已阻塞时的新事件唤醒。长度与切片解决旧历史混入，不能消除显示提示到进入等待之间的提前回复竞态。若需求要求提前回复也可靠生效，明确指出需要额外运行时能力。
- 空回复切片、用户取消、超时等只按已有能力和用户政策处理。不要虚构等待超时端口或取消事件。
- 提问后继续当前工具批次，还是为剩余调用记录跳过结果并重新规划，是业务政策。审核也需要用户明确的判定规则；提问工具的普通回复不自动代表授权。

## 哪些部件适合固化

| 固化层次 | 适合的内容 | 选择条件 |
|---|---|---|
| 当前 JSON 的本地函数 | 追加历史、记录工具结果、单次迭代中的分支处理 | 有重复调用、统一行为或必要返回边界 |
| 可展开的生成片段 | 提问与收集新回复、循环骨架、重复声明和连线 | 若编写环境支持生成器，最终仍展开为普通 JSON |
| 内置节点或运行时适配 | 消息编码、基础类型操作、调度与协议语义 | 属于跨任务稳定能力，现有组合不足或已证实成本值得优化 |
| workflow 配置或分支 | 审核、重试、停止、批次取消策略 | 会随用户目标、工具风险和业务规则变化 |

本地函数不会自动成为其他 workflow 可导入的库；复用片段也不是新的节点类型。只有在设计 SKILL 明确支持且用户提供依赖时，才能使用相应跨文件能力。

生成 workflow 时优先用现有能力完成任务。提出内置能力改进应说明现有组合的问题、拟议接口和行为影响；不要把提议混入可执行 JSON。尤其不要仅因希望缩短图，就把列表操作或业务政策写进调度器。

## 区分可读性收益和执行收益

- 函数提取通常减少主图复杂度，不会消除函数内部节点的调度和存储操作。单节点包装还可能增加调用与返回步骤。
- `Context read → list_append → Context write` 可以先封装以统一行为；封装不使读改写原子化。存在多个写入者时，需单独解决并发语义。
- 稳定工具定义可考虑初始化一次再复用；若工具可用性会变、需动态授权，或传递状态成本超过重建成本，则保留逐轮构造。
- 长历史的大列表复制、完整读写和模型上下文增长值得测量。截断前保护调用与结果的完整组，保留任务所需信息；不要只为减少节点而无条件裁剪历史。
- 正常单进程的串行调用顺序不保证外部副作用在崩溃或重试后只发生一次。只有任务要求时，才设计并验证幂等机制。

没有运行数据时说明结构上减少了什么，避免声称确定的性能提升。

## 交付前的经验检查

在设计 SKILL 的合法性检查之外，优先检查这些容易出错的行为：

- 循环能因什么条件结束？空列表、无调用和错误路径是否符合需求？
- 每个状态是否在合适的生命周期初始化？是否存在跨分支取值、上一轮数据残留或批次标志泄漏？
- 可选字段缺失和空值是否处理一致？无调用的 assistant 是否仍保留需要的 reasoning？
- 多工具调用是否逐个对应结果？拒绝、失败和跳过后能否合法进入下一轮？
- 提问恢复是否排除旧历史并保留全部新回复？是否把提前输入竞态误认为已解决？

若有相应工具，可验证静态契约、生成文件一致性、编辑器导入导出和真实进程的暂停/恢复。只有执行过才报告通过；模拟模型/工具的行为测试与真实供应商联调分别说明。没有验证环境时，根据两份 SKILL 审查并指出未验证依赖，不索取仓库才能完成设计。
