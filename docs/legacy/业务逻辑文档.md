 # AAgent 业务逻辑梳理文档

 ## 1. 项目概述

 **AAgent** 是一个基于 Docker Compose 运行的 QQ 机器人 + LLM Agent 系统。它通过 QQ 协议的 WebSocket 接收消息事件，将事件写入 Redis 队列，由 Agent 服务异步消费并调用大模型（DeepSeek）进行回复，同时把关键事件持久化到 MongoDB 形成历史上下文。

 核心能力：

 - 监听 QQ 私聊/群聊消息；
 - 对指定用户触发 LLM 多轮对话；
 - 支持 `/` 命令查询 API 余额、执行网络搜索；
 - 支持 LLM 调用工具（余额查询、Tavily 搜索）；
 - 使用 MongoDB 保存事件历史，供 LLM 上下文回忆。

 ## 2. 系统架构

 项目包含 5 个 Docker 服务（`qqbot` / `agent` / `webui` / `redis` / `mongodb`），通过 `docker-compose.yml` 编排，网络使用自定义桥接网络 `rainbow_net`。

 **服务拓扑、事件驱动设计、队列机制与事件流转详见《架构文档.md》。** 本文档聚焦各模块的业务逻辑细节。

 ## 3. 服务职责与核心模块

 ### 3.1 qqbot 服务

 入口：`listener.py`

 1. 使用 `websockets` 库连接到 `QQ_WS_URI`；
 2. 在请求头中携带 `Authorization: Bearer {QQ_WS_TOKEN}`；
 3. 循环接收 WebSocket 消息，解析 JSON；
 4. 对包含 `user_id` 的事件，封装为 `event_type=qq` 的任务；
 5. 通过 `queue_client.publish_to_queue()`（`LPUSH` 普通排队）写入 Redis 队列 `agent_tasks`。

 一个 QQ 事件被封装为：

 ```json
 {
   "event_type": "qq",
   "payload": {
     "user_id": "...",
     "group_id": "...",
     "raw_message": "...",
     "message": "..."
   }
 }
 ```

 ### 3.2 agent 服务

 入口：`task_worker.py`

 负责消费 Redis 队列中的事件，根据 `event_type` 分发处理：

 | 事件类型 | 处理说明 |
 |----------|----------|
 | `qq` | 调用 `user_interface()` 解析消息，判断是命令还是普通消息 |
 | `tool` | 调用 `execute_tool()` 执行指定工具，并将结果作为 `tool_return` 事件重新入队 |
 | `tool_return` | 仅记录历史，不主动触发回复 |
 | `active` | 调用 `chat_with_deepseek()` 进行大模型对话，并发送回复 |
 | `response` | 仅记录历史，不主动触发回复 |

 所有事件都会先写入 MongoDB（`record_history`），再执行后续逻辑。

 > **入队方式**：`qq` 事件在 `user_interface()` 中通过 `publish_to_queue()` 普通排队；`tool`、`tool_return`、`active` 等工具链内部事件通过 `insert_to_queue()` 最高优先级插队，确保一轮工具调用链不被新消息打断（详见 4.1）。

 #### 3.2.1 用户消息处理逻辑（`user_interface`）

 1. 读取 `raw_message`、`group_id`、`user_id`；
 2. 如果消息以 `/` 开头，按命令处理：
    - `/dsB`：查询 DeepSeek 余额；
    - `/kmB`：查询 Kimi 余额；
    - `/B`：同时查询 Kimi 与 DeepSeek 余额；
    - `/search <关键词>`：调用 Tavily 搜索，返回第一条结果的标题。
 3. 非命令消息时：
    - 若 `user_id` 等于 `QQ_TARGET_USER_ID`；
    - 且为私聊（无 `group_id`）或在群里被 `@`（消息包含 `[CQ:at,qq={BOT_ID}]`）；
    - 则通过 `publish_to_queue()` 发布一个 `event_type=active` 的事件（普通排队），触发 LLM 回复。

 #### 3.2.2 大模型对话逻辑（`chat_with_deepseek`）

 入口：`llm.py`

 1. 从 MongoDB 读取最近 10 条历史记录；
 2. 拼接 `system` 消息："你是一个办公助手"；
 3. 将历史记录转换为 OpenAI 兼容格式：
    - `qq` 事件 → `user` 角色；
    - `tool_return` 事件 → `tool` 角色；
    - `response` 事件 → `assistant` 角色（包含 `tool_calls` 时一并携带）；
 4. 调用 DeepSeek Chat Completions API，传入 `tools` 工具定义；
 5. 将模型返回的 `response` 事件、`tool` 事件、`active` 事件按顺序通过 `insert_to_queue()`（最高优先级插队）写入 Redis，保证工具链优先于后续新到的 QQ 消息被执行（详见 4.1）；
 6. 返回模型生成的文本内容。

 ### 3.3 工具模块（`tool.py`）

 已定义的工具列表（会被注册到 DeepSeek 的 `tools` 参数）：

 | 工具名 | 功能 | 来源 API |
 |--------|------|----------|
 | `get_deepseek_balance` | 查询 DeepSeek 账户余额 | `DEEPSEEK_BASE_URL/v1/user/balance` |
 | `get_kimi_balance` | 查询 Kimi 账户余额 | `KIMI_BASE_URL/v1/users/me/balance` |
 | `tavily_search` | 网络搜索 | `https://api.tavily.com/search` |

 额外包含但未注册到 LLM 的工具函数：

 - `bocha_search`：调用博查搜索 API，当前为独立函数，未接入 Agent 工具链。

 Tavily 支持多 Key 轮询：环境变量 `TAVILY_API_KEYS` 可配置逗号分隔的多个 Key，请求失败时自动切换。

 ### 3.4 QQ API 封装（`qqapi.py`）

 向 QQ HTTP API 服务（如 Lagrange/OneBot 实现）发送请求：

 - `send_group_msg(group_id, message)`：发送群消息；
 - `send_private_msg(user_id, message)`：发送私聊消息；
 - `send_private_img(user_id, img_bs64)`：发送私聊图片；
 - `get_group_list()`：获取群列表；
 - `get_group_member_info(group_id, user_id)`：获取群成员信息；
 - `get_group_msg_history(group_id, message_seq, count)`：获取群历史消息。

 所有请求均通过 `QQ_API_BASE_URL` 和 `QQ_API_TOKEN` 鉴权。

 ### 3.5 历史记录仓库（`history_repository.py`）

 使用 `pymongo` 连接 MongoDB，集合默认为 `agent.event_history`。

 主要方法：

 - `record_history(e)`：插入单条事件，附加 `created_at` UTC 时间；
 - `get_recent_history(limit=10, event_type=None)`：按时间倒序查询最近 N 条事件。

 已建立索引：

 - `created_at` 倒序；
 - `(event_type, created_at)` 复合索引；
 - `args.id` 稀疏索引（用于工具调用 ID 检索）。

 ## 4. 典型事件流转

 **完整的事件流转、状态机与队列机制（`publish_to_queue` 普通排队 / `insert_to_queue` 插队）详见《架构文档.md》第 3、4、5 节。**

 核心要点：

 - `response` 与 `tool_return` 事件本身不直接触发回复，仅用于更新历史上下文；
 - `active` 事件是真正触发 LLM 调用并发送 QQ 回复的入口；
 - LLM 工具调用链（`response → tool → tool_return → active`）通过 `insert_to_queue()` 插队保证不被新消息打断，循环直到 LLM 不再请求工具为止

 ## 7. 已知问题与优化建议

 ### 7.1 代码质量

 1. **源码编码问题**：部分 Python 文件中的中文字符串出现乱码（如 `print` 语句），建议统一保存为 UTF-8 并检查文件头编码声明。
 2. **文件头注释与实际文件名不符**：
    - `qqbot/listener.py` 顶部注释为 `# qqbot/task_publisher.py`；
    - `agent/qqapi.py` 顶部注释为 `# bot_api.py`。
    建议同步注释与文件名，避免维护困扰。
 3. **测试脚本含硬编码密钥**：`agent/script.py`、`agent/2.py`、`agent/3.py` 中直接写入了 API Key。生产环境应删除或重构为从环境变量读取，避免密钥泄露。
 4. **异常处理较粗糙**：部分接口调用未做细粒度异常分类与重试，网络抖动时可能导致任务失败。

 ### 7.2 业务逻辑

 1. **`/search` 命令仅返回标题**：当前实现只取搜索结果第一条的 `title`，建议返回更完整的摘要或链接，或支持用户选择结果数量。
 2. **`bocha_search` 未接入 Agent**：博查搜索函数已定义但未注册到 `tools` 列表，LLM 无法主动调用。
 3. **`ZAI_AP（设计意图已明确）**：`publish_to_queue()`（`LPUSH`）为普通排队、`insert_to_queue()`（`RPUSH`）为最高优先级插队、消费端统一 `BRPOP` 弹出——三者配合实现"外部消息排队、工具链插队"（详见 4.1）。建议在代码中补充注释固化该设计意图，避免被误认为方向不一致的 bug
 4. **队列顺序可读性**：`LPUSH` / `RPUSH` / `BRPOP` 混用导致事件处理顺序需要仔细推敲，建议统一入队方向或增加注释说明设计意图。
 5. **缺少幂等与去重**：如果 Redis 任务重复投递或 LLM 生成重复事件，可能导致重复回复。建议为事件添加唯一 ID 与去重机制。
 6. **无显式会话隔离**：历史记录按全局时间倒序读取，多用户/多群聊共用同一份上下文。若需支持多会话，建议按 `user_id` 或 `group_id` 分组查询历史。

 ### 7.3 部署与安全

 1. `.env` 文件已包含真实密钥，务必确保已加入 `.gitignore` 且不被提交。
 2. MongoDB 使用 root 账号，建议为应用创建最小权限独立用户。
 3. Redis 当前无密码，若部署到公网建议启用 `requirepass` 并限制网络访问。
 4. 建议增加健康检查与日志轮转，便于长期稳定运行。
