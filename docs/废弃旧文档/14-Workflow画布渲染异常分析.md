# Workflow 画布渲染异常分析

## 1. 问题描述

当 Workflow 节点数量从 14 个增加到 16 个附近时，画布出现渲染异常。典型表现可能包括：

- 新增节点看起来消失，实际被排到可视区域之外。
- 节点集中在画布右侧，连线位置不容易判断。
- 滚动画布后仍然无法自然地浏览全部节点。
- 节点数量增加后，连线或端口位置看起来不稳定。

本问题不是 Workflow 业务节点数量达到 16 后被后端拒绝，也不是解析器只支持 16 个节点。16 个节点只是触发了前端画布布局边界的一个偶然阈值。

## 2. 结论摘要

当前问题由三个层次叠加造成：

1. 自动布局只有 12 个预设位置。
2. 超过预设位置后，旧逻辑将所有后续节点继续放在同一行。
3. 画布和节点层使用固定的 `1800px × 1200px` 工作区，不能表达无限扩展的图。

本次已完成的修改属于局部止血：超过 12 个节点后改为多行布局，并根据节点坐标扩展节点层和连线层。它可以解决“第 13 个节点以后被横向推远”的直接问题，但还不能称为根治，因为画布仍然是正坐标、固定最小尺寸和 DOM 尺寸驱动的模型。

长期根治方向应是：把 Workflow 图数据、节点布局和编辑器视口拆成三个明确层次，并由统一的画布控制器负责坐标转换、工作区边界、缩放、聚焦和自动平移。

## 3. 根因链

### 3.1 12 个位置是隐含阈值

`webui_py/static/workflow/model.js` 中的 `nextNodePosition()` 预先生成 4 行 3 列位置：

```text
4 × 3 = 12 个位置
```

节点数量没有 16 的显式限制。新增第 13 个节点时，如果 12 个位置都被占用，旧逻辑进入退化分支：

```js
{ x: 52 + state.nodes.length * 210, y: 72 }
```

这会让节点数量越多，节点越远离左侧。第 16 个节点只是让这个问题足够明显，并不是问题的真正边界。

### 3.2 固定工作区放大了布局问题

`webui_py/static/css/workflow/canvas.css` 中，网格、连线层和节点层最低使用 `1800px × 1200px`。旧的 `node-layer` 还固定为 `height: 1200px`。

因此布局一旦继续向右或向下增长，就出现两个不一致：

- 节点模型中存在坐标。
- 画布 DOM 的可表达范围不足，用户未必能看到这些坐标。

这属于“数据存在但视图无法完整表达”的问题，单纯提高节点数量上限无法解决。

### 3.3 连线渲染依赖 DOM 几何位置

`webui_py/static/workflow/connections.js` 的 `renderConnections()` 会根据节点和端口的 DOM 几何位置计算 SVG 路径。只要节点层尺寸、滚动偏移、重绘时机或缩放坐标中有一处不一致，连线就可能表现为：

- 端点偏移。
- 路径被裁切或出现在错误位置。
- 节点首次渲染时没有正确连线，下一次交互后才恢复。

所以“节点排得下”不等于“画布渲染模型已经稳定”。

## 4. 已有修改的作用与边界

当前修改包含两部分。

### 4.1 溢出布局改为网格换行

超过原有 12 个预设位置后，节点改为 6 列继续换行：

```js
const overflowIndex = state.nodes.length - positions.length;
const column = overflowIndex % 6;
const row = Math.floor(overflowIndex / 6) + 4;
return { x: 52 + column * 258, y: 72 + row * 150 };
```

这解决了旧退化逻辑的直接缺陷，并让 16 个节点保持在一个可浏览的矩形区域内。

### 4.2 根据节点坐标扩展渲染层

渲染节点后，根据节点最大坐标设置节点层和连线层的宽高：

```js
const maxX = Math.max(1800, ...state.nodes.map((node) => node.x + 210));
const maxY = Math.max(1200, ...state.nodes.map((node) => node.y + 150));
```

这解决了固定 `height: 1200px` 对新增节点的裁剪问题。

但它仍有边界：

- 已加载的异常坐标不会自动重新布局。
- 节点只能在正坐标区域活动。
- 节点移动时如果其他代码依赖 CSS 固定尺寸，仍可能产生不同步。
- 没有缩放、适配全部节点和聚焦节点功能。
- 连接拖拽到视口边缘时不能自动平移。
- 依赖 DOM `getBoundingClientRect()` 的连线计算还没有统一的坐标转换层。

## 5. 为什么这不是 16 节点限制

当前系统中已知的数量限制与 Workflow 总节点数无关：

- WebUI 后端 `MAX_WORKFLOW_NODES` 为 200。
- `WorkflowRequest.nodes` 最多接受 200 个节点。
- 连线最多接受 1000 条。
- LLM 动态输入端口最多 20 个，是单节点端口限制。

因此应将问题命名为“画布布局和视口扩展缺陷”，而不是“Workflow 16 节点上限”。后一个命名会导致错误的修复方向，例如继续提高上限，却不改变画布的表达能力。

## 6. 根治方案

### P0：拆分三类状态

Workflow 编辑器应明确区分：

#### 业务状态

节点类型、节点配置、分支、连接等参与保存和版本同步的内容。

#### 布局状态

节点的 `x`、`y` 坐标。布局坐标可以保存，但不应和视口滚动位置混为一谈。

#### 视口状态

平移位置、缩放比例、当前选中节点。视口状态只影响查看方式，不应触发 Workflow 未保存提示。

建议由单独的 `viewport` 模块提供：

```js
const viewport = {
  x: 0,
  y: 0,
  zoom: 1,
};
```

所有节点拖拽、端口命中、连线预览、框选和定位都使用：

```js
screenToCanvas(screenPoint, viewport)
canvasToScreen(canvasPoint, viewport)
```

不能在不同文件中分别拼接 `scrollLeft`、`scrollTop` 和缩放比例。

### P1：动态工作区而不是固定大画布

工作区应由以下内容共同决定：

- 所有节点的包围盒。
- 连线预留空间。
- 当前视口范围。
- 四周安全边距，建议至少 320px。

计算出的边界应集中在画布控制器中更新。向右下扩展时直接增加工作区；向左上扩展时需要同步调整画布原点，不能把所有节点强行限制为正坐标。

扩展逻辑必须有上限或采用分块策略，避免通过无限增大单个 DOM 元素造成重绘和内存问题。

### P1：统一重绘生命周期

建议将渲染拆为明确顺序：

1. 更新节点 DOM。
2. 测量节点和端口几何位置。
3. 更新工作区边界。
4. 使用统一坐标转换计算连线路径。
5. 在同一个 `requestAnimationFrame` 周期内完成视图更新。

节点配置变化、节点拖动、节点新增、节点删除和视口变化都应走同一个刷新入口，而不是各自调用局部重绘。

### P1：补齐大画布交互

至少需要：

- “适配全部节点”。
- “聚焦选中节点”。
- `Ctrl/Cmd + 滚轮` 缩放。
- 连接拖拽时靠近边缘自动平移。
- `Escape`、`pointercancel`、窗口失焦时清理临时拖拽状态。

这些功能不是视觉装饰，而是节点数量增长后保持可用性的基础能力。

## 7. 验证方案

### 7.1 布局回归

至少验证节点数量：4、12、13、16、24、50。

每个数量都检查：

- 所有节点都有唯一 DOM 元素。
- 所有节点位于工作区包围盒内。
- 节点之间没有因自动布局产生不可接受的重叠。
- 横向和纵向滚动都能访问全部节点。
- 节点层和连线层尺寸一致。

### 7.2 连接回归

对控制线、内容线、Message 线和列表线分别验证：

- 端点连接到正确端口。
- 节点移动后连线立即更新。
- 滚动后连线不发生偏移。
- 删除节点后不会残留路径。
- 新增节点并连接到视口外节点时可以完成拖拽。

### 7.3 数据回归

保存、刷新和重新加载 16 个节点的 Workflow，确认：

- 节点数量不变。
- 节点配置不变。
- 连接数量和端口不变。
- `x`、`y` 布局坐标恢复。
- 视口状态不会污染 Workflow 业务 JSON。

### 7.4 最小自动化检查

当前仓库没有发现 Workflow 专用的前端测试入口。建议先增加一个纯函数测试，覆盖 `nextNodePosition()`：

```text
节点 1 到 12：使用预设位置
节点 13 到 18：进入第二布局区域并按列换行
新增节点：不与已有节点重叠
```

随后再增加浏览器级测试，验证实际 DOM 节点数、画布尺寸和连线路径数量。只有浏览器级测试才能发现“数据坐标正确但视觉不可见”这类问题。

## 8. 处理优先级

建议按以下顺序实施：

1. 保留当前网格换行补丁，避免 16 节点立即不可用。
2. 抽取 `viewport` 和坐标转换模块。
3. 将工作区边界计算集中到画布控制器。
4. 统一节点、端口和连线的刷新生命周期。
5. 增加适配全部节点、聚焦节点和缩放。
6. 增加连接拖拽边缘自动平移。
7. 增加 16、24、50 节点的浏览器回归测试。

## 9. 最终判断

这次问题可以通过当前补丁缓解，但不能靠“再增加几个预设位置”根治。真正的问题是编辑器把一个可增长的图，放进了固定尺寸、缺少统一视口模型的画布中。

因此，16 个节点不是需要记住的特殊数字。后续设计应以“节点数量可增长、坐标可扩展、视口独立、连线始终使用统一坐标系”为验收标准。
