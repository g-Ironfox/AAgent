# 06 格式规范

> 本文集中定义 AAgent 的全部格式约定，作为**唯一的格式说明**，其他文档不再重复赘述、只链接回本文件：
>
> 1. **事件格式**（第 1 节）：事件信封与各事件类型的 payload；
> 2. **上下文格式**（第 2 节）：历史事件如何投影为 LLM 消息、排序与截断；
> 3. **工具消息格式**（第 3 节）：工具结果如何进入上下文、注册工具一览与设计取舍。
>
> 涉及代码：`agent/task_worker.py`、`agent/tool.py`、`agent/llm.py`、`qqbot/listener.py`、`webui_py/main.py`。前端 API 格式见 [webUI/前端API格式](webUI/前端API格式.md)。

## 1. 事件格式

### 1.1 事件信封

所有事件统一为如下结构：

```json
{
  "event_type": "<类型>",
  "payload": { "...": "..." }
}
```

- `event_type`：事件类型字符串，见 1.2；
- `payload`：该类型的业务负载；
- 入队后由 `record_history()` 追加 `created_at`（UTC ISO 字符串），MongoDB 另有 `_id` 作为稳定排序键；
- Worker 弹出事件后**先 `record_history()` 写入 MongoDB，再按 `event_type` 分发**（详见 [02-事件与队列](02-事件与队列.md)）。

### 1.2 各事件类型的 payload

| 事件 | 产生方 | 入队方式 | payload 字段 | 消费行为 |
|------|--------|----------|--------------|----------|
| `qq` | `qqbot/listener.py` | `publish`（LPUSH） | `post_type`、`user_id`、`group_id`、`raw_message`、`message` | `user_interface()` 判断命令 / 授权 |
| `webui` | WebUI `POST /api/terminal` | `RPUSH` | `message`、`files` | 记录历史 → 发布空 `active` |
| `active` | `user_interface()` / webui 分支 / active 分支 | 前者 `publish`，后两者 `insert` | `{}`（QQ 触发时带 `user_id`、`group_id`） | `chat_with_deepseek()` → 生成 `response` |
| `response` | active 分支 | `insert`（RPUSH） | `content`、`reasoning`、`tool_calls`、`context` | 记录历史；有 `tool_calls` 时逐个生成 `tool` |
| `tool` | response 分支 | `insert` | `id`、`tool`、`args` | `execute_tool()` → 生成 `tool_return` |
| `tool_return` | `task_worker.py` | `insert` | `id`、`tool`、`args`、`result`、`success` | 仅记录历史（供 LLM 上下文 callback） |

各事件 payload 细节：

**`qq`**（`listener.py::parse_event`）

- `post_type = "message"` 时：`user_id`（int）、`group_id`（int | None）、`raw_message`（str）、`message`（OneBot 消息数组）；
- `post_type = "inputing"`（输入状态通知）：仅 `user_id`；
- 其余 `notice` 事件不封装。

**`webui`**（`webui_py/main.py::submit_terminal`）

```json
{
  "event_type": "webui",
  "time": "<RFC3339 毫秒 Z>",
  "payload": { "message": "...", "files": [] }
}
```

- `message` 非空且 ≤ 4000 字符；`files` 当前恒为空数组（暂不支持附件）。

**`active`**

- 由 webui 分支或 active 分支生成时 payload 为空对象 `{}`，只承担“请 LLM 推理”的脉冲，不携带任何消息内容；
- 由 `user_interface()`（QQ 授权用户）生成时携带 `user_id`、`group_id`。

**`response`**

```json
{
  "event_type": "response",
  "payload": {
    "content": "...",
    "reasoning": "...",
    "tool_calls": [],
    "context": [ "...本次组装给 LLM 的 messages..." ]
  }
}
```

- `content` 可为空字符串（工具轮）；`reasoning` 为模型推理内容；`tool_calls` 为 DeepSeek 返回的 tool_calls 数组（无则 `[]`）；`context` 为本次组装的消息数组（调试用）。

**`tool`**

```json
{
  "event_type": "tool",
  "payload": {
    "id": "<tool_call_id>",
    "tool": "<函数名>",
    "args": { "...": "..." }
  }
}
```

- `args` 由 response 分支对 `tool_calls[].function.arguments` 做 `json.loads` 得到；
- 解析失败时**不生成 `tool` 事件**，直接生成 `success=False` 的 `tool_return`，`result` 为 `Error: 工具参数 JSON 解析失败`，不打断工具链。

**`tool_return`**

```json
{
  "event_type": "tool_return",
  "payload": {
    "id": "<tool_call_id>",
    "tool": "<函数名>",
    "args": { "...": "..." },
    "result": "<字符串>",
    "success": true
  }
}
```

- `result` 统一为字符串：列表 / 字典经 `json.dumps` 序列化，`None` 替换为 `执行失败，未获取到数据`，异常时 `success=False` 并带 `Error: ...` 前缀。

规划中的事件类型：`async_request` / `async_result`，协议见 [05-路线图与创新](05-路线图与创新.md#25-异步任务兼容)。

### 1.3 记录、排序与生命周期

- 所有事件共用 `record_history()` 入口，附加 `created_at`（UTC）；
- 历史查询按 `_id` 倒序（保证同毫秒内插入顺序稳定；`created_at` 索引仍保留，见 [01-系统架构](01-系统架构.md)）；
- 事件既是“调度触发器”也是“信息载体”，两层解耦见 [07-事件双重身份与信息回调](07-事件双重身份与信息回调.md)。

## 2. 上下文格式（LLM 消息投影）

系统把 LLM 上下文建立在 MongoDB 事件历史的“最近 N 条”之上（当前 N=10）。`task_worker.py` 的 active 分支把历史事件逐条投影为消息，组装完成后交给 `llm.py::chat_with_deepseek()` 发送。

### 2.1 投影规则

| 历史事件 | 上下文角色 | 内容 |
|----------|-----------|------|
| `qq`（message） | `user` | `<QQ event='msg' type='group' group_id=... sender_id=...>...</QQ>` 或 `<QQ event='msg' type='private' sender_id=...>...</QQ>` |
| `webui` | `user` | `<Msg role='admin'>payload["message"]</Msg>` |
| `tool_return` | `user` | `Tool {tool} args({json.dumps(args)}) result: {result}` |
| `response` | `assistant` | `payload["content"]`（为空时用 `""`） |

- 首条固定为系统提示 `{"role": "system", "content": "你是一个办公助手"}`；
- `active` 与 `tool` 事件会记录历史但**不投影**为 LLM 消息；
- `webui` 以 `user` 角色 + `<Msg role='admin'>` 标记进入上下文（终端最高权限的信息语义，见 [08-终端设计](08-终端设计.md)）。

### 2.2 排序与截断

- 取最近 10 条（`get_recent_history(limit=10)`，按 `_id` 倒序）后**反转为正序**逐条投影，保证消息时间顺序；
- 这对应 callback 的三层筛选：投影（只映射 `qq` / `webui` / `response` / `tool_return`）→ 排序（时间顺序）→ 截断（前 N 条），详见 [07-事件双重身份与信息回调](07-事件双重身份与信息回调.md)。

### 2.3 为什么不用 `tool` 角色

工具链事件（`response → tool → tool_return`）天然成组出现，而截断窗口可能恰好落在组内：

- 保留了 `assistant(tool_calls)` 却丢了它的工具结果；
- 或者留下孤悬的工具结果，却没有对应的 `assistant(tool_calls)`。

OpenAI 兼容 API 对这两种序列都会返回 400，且失败发生在上下文组装阶段、无法通过重试当前请求修复。因此本方案的关键取舍（两点缺一不可）：

1. `tool_return` 不使用原生 `tool` 角色，而是折叠成 `user` 文本；
2. 投影到上下文的消息中 `response` 不再携带 `tool_calls` 字段（事件本身仍保留 `tool_calls` 供 worker 生成 `tool` 事件）。

于是消息序列中**不存在任何配对约束**，截断天然免疫——这是本方案的全部意义。前一轮尝试过的“成对截断”方案（逐条扫描补全消息对）逻辑繁琐、边界情况多，已被本方案取代。

## 3. 工具消息格式

### 3.1 追溯证据链：为什么不丢信息

改用 `user` 文本**不等于丢失信息**。证据链由两层保证：

- **权威层（结构化存档）**：MongoDB 的 `tool_return` 事件始终保留完整的结构化数据（`id` / `tool` / `args` / `result` / `success` / `created_at`），任何时刻都可以按 `payload.id` 检索；
- **投影层（LLM 上下文）**：把同一份数据折叠为 `Tool {tool} args({args}) result: {result}`，模型在推理时能看到“调用了什么工具、传入什么参数、得到什么结果”的完整闭环。

即：**上下文是证据链的文本投影，MongoDB 是证据链的结构化存档**。两者内容一致、只是形态不同——“追溯”不被打断靠的是这份一致性，而不是 `tool_call_id` 的协议配对。

### 3.2 方案对比

| 方案 | 做法 | 截断安全性 | 证据链 | 复杂度 |
|------|------|-----------|--------|--------|
| 原生 `tool` 角色 | `tool_return` → `tool`，`tool_call_id` 配对 | 差，截断即 400 | 结构化，但依赖配对 | 需成对截断兜底，复杂 |
| 丢弃工具结果 | `tool_return` 不进上下文 | 安全 | 断裂，模型不知道工具执行过 | 极简，但不可用 |
| **本方案（已采用）** | `tool_return` → `user` 文本，投影消息去 `tool_calls` | 天然安全 | 完整：工具名 + 参数 + 结果 | 几条映射规则 |

### 3.3 代价与已知边界

- **丢失 `tool_call_id` 的结构化关联**：模型无法精确引用“第 N 次工具调用”，但对当前文本型工具（余额、搜索）无影响；需要时仍可从 MongoDB 按 `payload.id` 检索；
- **工具轮的 `assistant` 消息 content 通常为空**：当前实现会写入 content 为空的 `assistant` 消息（`payload["content"] or ""`），各兼容 API 接受空字符串；若未来某模型拒绝，可在此处补 `(调用工具)` 占位；
- **投影位置**：事件到消息的映射实现在 `task_worker.py` 的 active 分支（已显式 `import json`）；`llm.py` 只负责把组装好的 `messages` 发送给模型。

### 3.4 注册工具一览

注册到 DeepSeek `tools` 参数的工具（`agent/tool.py`）：

| 工具名 | 功能 | 参数（properties） | required |
|--------|------|--------------------|----------|
| `get_deepseek_balance` | 查询 DeepSeek API 账户余额 | 无 | — |
| `get_kimi_balance` | 查询 Kimi API 账户余额 | 无 | — |
| `send_group_msg` | 发送群消息 | `group_id`(string)、`message`(string) | `["group_id", "message"]` |
| `send_private_msg` | 发送私聊消息 | `user_id`(string)、`message`(string) | `["user_id", "message"]` |
| `tavily_search` | 使用 Tavily 搜索引擎进行网络搜索 | `keyword`(string) | `["keyword"]` |

其他说明：

- 来源 API：DeepSeek `/v1/user/balance`、Kimi `/v1/users/me/balance`、Tavily `https://api.tavily.com/search`；
- Tavily 支持多 Key 轮询：`TAVILY_API_KEYS` 逗号分隔，请求失败自动切换；
- `bocha_search`：独立函数，**未注册**到工具链；
- `execute_tool(id, tool, args)` 分发执行，结果统一转字符串，未知工具返回 `未知工具: {tool}`。
