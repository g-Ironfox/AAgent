# 进程与工作区文件权限

权限等级是非负整数，数值越大权限越高。读、写分别比较：

- 进程读等级 ≥ 文件要求读等级，才允许读取。
- 进程写等级 ≥ 文件要求写等级，才允许修改、重命名、钉住或删除。

每个工作区文件在文件记录中保存两组读写等级，以及三个独立的 checkpoint 布尔权限，与文件内容独立：

```json
{
  "permissions": {
    "runtime": { "read": 3, "write": 2 },
    "required": { "read": 1, "write": 2 },
    "checkpoints": { "read": false, "create": false, "restore": false }
  }
}
```

`runtime` 决定执行这个文件中的 Workflow 时，进程取得的读写等级。
`required` 决定其他进程访问这个文件时，需要达到的读写等级。
这两组等级独立设置，不会彼此限制。
`checkpoints` 决定执行该 Workflow 时进程的 checkpoint 能力，不是访问该文件所需的权限。

## 创建与继承

从 WebUI 创建根进程时，提交的 Workflow 内容及其权限形成同一个启动快照。
子进程加载工作区 Workflow 文件时，先按父进程的读等级检查该文件是否可读，再从同一次读取结果取得内容及权限。
子进程直接采用该文件的 `runtime` 和 `checkpoints`，不以父进程等级或 checkpoint 权限作为上限。
因此，一个父进程可以通过可读的高权限 Workflow 创建等级高于自己的子进程。

进程创建文件时，两组权限都继承创建进程的运行权限。例如运行等级为读 3、写 2，则新文件的 `runtime` 和 `required` 都是读 3、写 2。
新文件的三个 checkpoint 权限也继承创建进程；旧配置缺失的项默认 `false`。
修改已有文件会保留它原有的权限。
进程不能通过文件工具自行指定或修改权限元数据；管理员可在工作区文件编辑界面修改四个等级和三个 checkpoint 开关。

运行中的进程持有启动时的权限快照。之后修改 Workflow 文件权限，不会追溯改变已有进程。
已有文件及缺少权限的旧进程默认读写等级均为 0；管理员新建文件的默认等级也为 0。

## 执行与持久化

Workflow 的工作区工具和子 Workflow 加载请求自动携带进程身份及随机令牌。
`agent_environment` 从 Redis 内核库的进程表读取实际等级，校验身份，并对每次文件操作检查权限。
文件列表仅返回该进程可读的文件；权限不足的直接文件操作返回 HTTP 403。
无效身份、错误令牌或已结束进程的令牌同样会被拒绝。

文件权限随 MongoDB 文件记录保存，也包含在检查点快照、恢复及差异中。
checkpoint 操作分别检查三个独立开关，文件读写等级再高也不会自动获得这些能力：

| 开关 | 允许的操作 |
| --- | --- |
| `read` | 列表、分支树、父 checkpoint 查询、差异 |
| `create` | 创建全工作区快照 |
| `restore` | 恢复整个工作区，包括文件内容及权限；允许恢复到空工作区（seq=0） |

三个开关互不隐含，缺省均为 `false`，严格接受布尔值。根进程、子进程及新建文件都取得独立快照；修改文件配置不改变已启动进程的权限。

进程创建 checkpoint 时，响应仅返回事件元数据，不包含全工作区文件内容。快照本身仍保存完整工作区，之后的差异读取会同时检查文件在差异两侧和当前工作区的读取门槛；任一侧不可读的文件不会返回差异。列表和分支树只提供 checkpoint 元数据。

`restore=true` 是全工作区恢复能力，不受逐文件写等级限制，也不要求 `read` 或 `create`。恢复会移除快照之后新增的文件、恢复旧权限并重新分配文件 revision，保留已有 checkpoint 历史，但不会自动保存尚未建立 checkpoint 的当前修改，也不恢复运行中的进程状态。

通用工作区事件历史接口 `/api/files/events` 仍只对管理端开放，避免原始事件快照暴露文件内容；工作流使用受过滤的 checkpoint 查询接口。
`agent_runtime` 与 `agent_environment` 必须使用一致的 Redis 地址、`REDIS_KERNEL_DB` 及 `ProcessTable` 配置；Compose 已传入这些配置。

## 信任边界

这是 Workflow 执行器中的应用层权限。当前执行环境 API 沿用受信任管理端模型：未携带进程身份头的文件 API 请求具有管理权限。
因此应将管理 API、Redis 和 MongoDB 放在受信任的访问范围内；任意代码执行、外部工具自行访问 HTTP 或数据库不在这套检查的隔离范围内。
如果要对不受信任代码建立强隔离，还需要单独的管理端认证和网络／操作系统沙箱。
