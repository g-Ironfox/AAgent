# WebUI 前端事件流重构设计

> 本文是 WebUI 重构时的设计与验收记录,不是当前 API 参考。当前实现继续使用 `/api/events` 的 `items` 混合数组契约,前端按 `status` 分区;已落地的优化过程见[前端优化记录](前端优化记录.md)。

## 1. 目标

WebUI 是 Agent 运行状态的观察窗口，不是通用任务管理器。首页只回答三个问题：

1. 过去执行了什么？
2. 现在正在执行什么？
3. 接下来将执行什么？

页面采用一条从上到下、从过去到未来的连续事件流，不再把事件做成可以任意混排的状态表格。

## 2. 核心不变量

> Event 不是在 MongoDB 中，就是在 Redis 中。所有未执行的 Event 都在 Redis 中；MongoDB 中的 Event 都是已执行或正在执行的 Event。

前端设计和实现必须服从这条不变量：

- Redis 是“未来”：其中的 Event 一律显示为等待执行。
- MongoDB 是“现在和过去”：其中的 Event 只能显示为正在执行或执行历史。
- Worker 状态用于从 MongoDB 记录中识别当前正在执行的 Event，不创造第四种事件归属。
- `pending`、`running`、`done` 是存储状态的前端投影，不是独立维护的业务状态。
- 前端不得根据时间、事件类型或文案猜测 Event 状态。
- 即使接口返回顺序发生变化，前端也必须维持“历史 → 正在执行 → 等待执行”的固定结构。

### 2.1 状态映射

| 存储位置 | Worker 当前事件 | 前端阶段 | 展示名称 |
|---|---:|---|---|
| MongoDB | 否 | `done` | 执行历史 |
| MongoDB | 是 | `running` | 正在执行 |
| Redis 队列 | 否 | `pending` | 等待执行 |

Worker 从队列取出 Event 后，Event 会出现在 Redis 的 Worker 状态中，并在开始处理时写入 MongoDB。接口需要用内容指纹合并这两个观测来源，前端只展示一个“正在执行”事件。

### 2.2 五种数据状态

MongoDB、Redis 和 Worker 是三个相互关联但含义不同的观测面。MongoDB 中可能同时包含历史事件和当前正在处理的事件；Redis 只表示尚未被 Worker 取走的未来事件；单 Worker 的“正在执行”只能是 0 或 1。不能仅根据 MongoDB 是否为空来判断 Worker 是否正在执行。

| 状态 | MongoDB | Redis 队列 | Worker | 业务含义 | 页面投影 |
|---:|---|---|---|---|---|
| 1 | 空 | 空 | 空闲/未上报 | 系统没有历史、没有未来任务，当前也没有执行任务 | 历史 0，正在执行 0，等待 0 |
| 2 | 有，仅当前事件 | 空 | 正在执行 | Worker 已取出唯一任务并开始处理，尚无历史完成记录，也没有未来任务 | 历史 0，正在执行 1，等待 0 |
| 3 | 有历史和当前事件 | 空 | 正在执行 | 有执行历史，Worker 当前正在处理一个任务，队列中没有未来任务 | 历史大于 0，正在执行 1，等待 0 |
| 4 | 有历史 | 空 | 空闲/未上报 | 有执行历史，当前没有正在执行的任务，也没有未来任务 | 历史大于 0，正在执行 0，等待 0 |
| 5 | 有历史和/或当前事件 | 有未来事件 | 正在执行或空闲 | 系统存在未来队列；Worker 可能正在处理一个任务，也可能已空闲 | 历史按 MongoDB 统计，正在执行为 0 或 1，等待为 Redis 队列长度 |

其中状态 2 和状态 3 都是“MongoDB 有、Redis 空、Worker 正在执行”，区别只在于 MongoDB 是否已经有完成历史；状态 3 的“有执行”指当前 Worker 执行，不是 MongoDB 中存在任意记录。状态 5 覆盖队列非空的两种 Worker 子状态，页面必须分别读取 Worker 状态，不能把 Redis 有数据直接等同于 Worker 正在执行。

概览中的“正在执行”是单 Worker 的布尔计数：空闲、未上报或异常但未确认正在处理时显示 `0`，`processing` 时显示 `1`。它不是“MongoDB / Worker 的数量”，也不是 MongoDB 记录数；因此界面文案应表达“当前任务 0/1”，不能显示成容易误解的“正在执行 0 MongoDB / Worker”。

## 3. 信息架构

页面主体只保留一个事件流，不使用“全部 / 进行中 / 将进行 / 已处理”状态标签切换。状态标签会把完整时间线切碎，也会弱化存储不变量。

```text
┌──────────────────────────────────────────────┐
│ 顶栏：AAgent / 连接状态 / 刷新控制           │
├──────────────────────────────────────────────┤
│ 运行概览：历史数 / 正在执行 / 等待数         │
├──────────────────────────────────────────────┤
│ 搜索 / Event 类型筛选                        │
├──────────────────────────────────────────────┤
│ 执行历史                                     │
│   较早的记录                                 │
│   ...                                        │
│   最近完成的记录                             │
├══════════════════════════════════════════════┤
│ 正在执行                                     │
│   当前 Event / 已运行时间 / Worker 状态      │
├══════════════════════════════════════════════┤
│ 等待执行                                     │
│   下一项                                     │
│   等待 #2                                    │
│   ...                                        │
└──────────────────────────────────────────────┘
```

三个区段始终存在。没有数据时显示区段自己的空状态，不用一个覆盖整张列表的统一空白页。

## 4. 排序规则

整条事件流的阅读方向是从上到下：过去 → 现在 → 未来。

### 4.1 执行历史

- 历史区位于最上方。
- 较早记录在上，最新完成记录在下。
- 最新完成记录必须紧邻“正在执行”区，使现在之前发生的最后一件事最容易看到。
- 接口可以按时间倒序读取 MongoDB，但展示前必须按时间正序排列。

### 4.2 正在执行

- 正在执行区固定处于历史与等待队列之间。
- 单 Worker 架构下最多显示一个 Event。
- Worker 空闲时仍保留该区段，显示“当前无执行事件”，避免上下区域突然拼接造成位置跳动。
- 正在执行超过阈值时显示“疑似卡死”，但 Event 阶段仍是正在执行，不能移动到其他区域。

### 4.3 等待执行

- 等待区位于最下方。
- Redis 下一次将弹出的 Event 排在最上，标记“下一项”。
- 后续 Event 按真实消费顺序向下排列，显示“等待 #2、#3……” 。
- 新 Event 入队时，不得导致已有等待行的身份变化或展开状态丢失。

## 5. 页面布局

### 5.1 顶栏

保留以下全局控制：

- AAgent 标识；
- API 连接状态；
- 自动刷新间隔；
- 暂停 / 继续刷新；
- 立即刷新。

顶栏保持紧凑，不承担事件解释功能。

### 5.2 运行概览

概览采用一条紧凑状态带，不使用可点击的状态卡片：

- 执行历史：当前已加载的 MongoDB 记录数；
- 等待执行：Redis 队列总长度；
- Worker：执行中、空闲、尚未上报、不可用、疑似离线或疑似卡死；
- 最后同步时间。

“正在执行”区段本身已经明确展示当前事件或空状态，因此概览不再重复放置“当前任务 0/1”统计。统计只负责快速扫视，不再充当筛选入口。

### 5.3 筛选工具

只保留全局搜索和 Event 类型筛选。筛选后的结果仍然放回原来的三个区段，绝不混成一个列表。

- 搜索范围：完整 Event JSON；
- 类型筛选：`event_type`；
- 筛选不隐藏区段标题；
- 区段无匹配项时显示“无匹配事件”，区别于数据本身为空。

### 5.4 Event 行

所有阶段使用同一种基础行结构，减少认知切换：

- 阶段标识；
- `event_type`；
- 内容摘要；
- 关键标识，如 tool call ID、user ID 或 message ID；
- 时间或队列位置；
- 展开详情按钮；
- 展开后的完整 JSON。

阶段差异通过左侧标记、背景和辅助信息表达，不改变行的列结构。

## 6. 视觉方向

这是运行控制台，视觉应安静、紧凑、适合持续观察：

- 使用浅色中性背景和清晰边界，避免大面积单一色调；
- 历史使用低对比中性色；
- 正在执行使用高辨识度琥珀色，并保留克制的运行指示动画；
- 等待执行使用冷蓝色；
- 正常 Worker 状态使用绿色，异常使用红色；
- 正在执行区是全页视觉锚点，但不做成独立浮动卡片；
- 桌面端保持高信息密度，移动端改为纵向字段，不允许文字或按钮重叠；
- 展开详情不得改变其他 Event 的展开状态。

## 7. 数据契约

曾建议 `/api/events` 明确返回分区，而不是让前端依赖混合数组的偶然顺序：

```json
{
  "queue": "agent_tasks",
  "fetched_at": "2026-08-01T12:00:00Z",
  "worker": {},
  "summary": {
    "history": 20,
    "running": 1,
    "pending": 6
  },
  "sources": {
    "mongodb": "ok",
    "redis": "ok",
    "worker": "ok"
  },
  "history": [],
  "running": null,
  "pending": [],
  "warnings": {}
}
```

`summary.history` 表示当前接口加载的 MongoDB 历史窗口，不是整个集合的总数。`sources` 用于区分真实的 0 和数据源不可用：`mongodb` / `redis` 可为 `ok` 或 `unavailable`，`worker` 可为 `ok`、`missing`、`unavailable` 或 `invalid`。来源不是 `ok` 时，前端显示不可用状态或 `--`，不能显示成“没有记录”的 0。

当前保留 `items` 契约,前端会先按 `status` 分区,再按本设计排序,不直接依赖接口数组的偶然顺序。

### 7.1 身份稳定性

- MongoDB 历史 ID：应优先使用 MongoDB `_id`；若接口不暴露 `_id`，继续使用内容指纹与创建时间组合。
- 正在执行 ID：使用 Event 内容指纹，确保 Redis Worker 状态与 MongoDB 记录合并为同一条。
- Redis 等待 ID：使用“内容指纹 + 相同内容在消费顺序中的序号”，不能使用 Redis 数组下标。

## 8. 状态迁移与动画

一个 Event 的正常视觉路径是：

```text
Redis 等待区 → Worker 取出 → MongoDB 正在执行区 → MongoDB 执行历史区
```

- 刷新时在同一区段内复用相同 ID 的 DOM 节点，避免未变化的行重复播放入场动画。
- 等待 Event 开始执行时，从等待区移除，并在中间执行区创建 running 行。
- 执行完成时，running 行被移除，历史区底部创建 done 行。
- 当前没有实现节点跨区移动或 FLIP 迁移动画；新建的目标行只播放 `.enter` 入场动画，初次加载的新行也会播放该动画。
- 用户启用 `prefers-reduced-motion` 时关闭行入场动画和正在执行标记的脉冲动画。

## 9. 降级与异常

不同数据源故障时，保留仍然可信的区段：

- MongoDB 不可用：历史区显示不可用，Redis 等待区继续展示。
- Redis 不可用：等待区和 Worker 状态显示不可用，已读取的历史继续展示。
- Worker 状态缺失：正在执行区显示“Worker 未上报”，不能把 MongoDB 最新记录猜成正在执行。
- 接口完全不可用：保留最后一次成功快照并标记为过期，不清空页面。
- Worker 状态中的 Event 与 MongoDB 暂时未匹配：可短暂以 Worker 状态展示正在执行，但应显示数据仍在同步。

## 10. 响应式要求

- 桌面端：三个区段共用列宽，便于纵向比较。
- 平板端：隐藏表头，将来源和时间移至摘要下方。
- 手机端：Event 行改为单列信息流，详情按钮固定在标题行右侧。
- 正在执行区、队列位置和展开按钮必须有稳定尺寸，轮询更新不能引发布局跳动。
- 任意宽度下，长 Event 类型、ID 和 JSON 内容都不能撑破容器。

## 11. 实施范围

本次重构预计涉及：

- `webui/events.go`：按存储语义生成稳定分区和顺序；
- `webui/static/index.html`：重建单时间轴页面结构；
- `webui/static/app.js`：调整状态、筛选、轮询和过期快照逻辑；
- `webui/static/render.js`：实现三区段渲染及同区段 DOM 节点复用；
- `webui/static/styles.css`：按新信息架构重写桌面与移动端样式；
- `webui/static/api.js`：仅在 API 契约变化时调整。

不改变 Redis 消费顺序、Agent 执行逻辑和 MongoDB 历史写入逻辑。

## 12. 验收标准

1. 页面从上到下始终是执行历史、正在执行、等待执行。
2. 历史中最新完成的 Event 最靠近正在执行区。
3. Redis 下一项最靠近正在执行区，其余按真实消费顺序向下排列。
4. 正在执行 Event 只出现一次，不同时出现在历史区。
5. 三个区段在空闲、筛选无结果或部分数据源失败时仍保持结构稳定。
6. 自动刷新不重置已展开详情，不让未变化的行重复播放进入动画。
7. 暂停刷新后页面明确显示暂停状态，手动刷新仍可用。
8. 桌面和手机布局无文字、按钮或详情内容重叠。
9. 前端不使用时间或内容猜测阶段，所有阶段都可追溯到 MongoDB、Redis 和 Worker 状态。
10. Go 构建、JavaScript 语法检查和浏览器桌面 / 手机视图验证通过。
