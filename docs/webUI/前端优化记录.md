# WebUI 轮询刷新优化记录

> 2026-07-31，2026-08-01，2026-08-02 按当前实现复核。WebUI 默认每 2s 轮询一次，也可选择 0.5s、1s、3s、5s 或 10s。本文记录事件页和终端的已落地前端优化，并说明当前实现对滚动位置的实际保证。完整事件流设计见[前端事件流设计](前端事件流设计.md)。

## 一、列表闪烁

旧实现中，每轮轮询时整个事件列表会"闪"一下。轮询频率会影响出现次数，但不是动画重播的直接原因。

### 根因

三条代码合谋造成的：

1. **CSS**：入场动画原本挂在 `.event-row` 选择器上，每行都有 `animation:reveal 220ms`
2. **JS**：`renderSection()` 每轮都执行 `section.list.replaceChildren(fragment)`，整表重建
3. **浏览器行为**：持有动画样式的节点被移出文档再插回后，动画可能重新开始

当前渲染流程会先把已有节点 `append` 到 `DocumentFragment`，再调用 `replaceChildren` 写回列表。若所有 `.event-row` 都永久持有入场动画，这种移出再插回会让动画重复出现；轮询返回的行越多，视觉闪烁越明显。

### 修复（三步）

### 第一步：动画从行选择器移到独立 class

`webui/static/styles.css`：

```css
/* 原来：动画挂在行上，每行都有 */
.event-row { animation:reveal 220ms ease both; }

/* 修复：动画只属于 .enter，复用行不持有 */
.event-row.enter { animation:reveal 220ms ease both; }
```

`@keyframes reveal` 不变：

```css
@keyframes reveal {
  from { opacity:0; transform:translateY(4px); }
  to   { opacity:1; transform:translateY(0); }
}
```

### 第二步：新建行加 `.enter`，播完即删

`webui/static/render.js` `createEventRow()`：

```js
function createEventRow(item) {
  const row = document.createElement('article');
  row.className = 'event-row';
  row.dataset.id = item.id;
  row.classList.add('enter');                                             // ← 只有新建行
  row.addEventListener('animationend', () => row.classList.remove('enter'), { once: true });
  // ...innerHTML 填充...
}
```

正常动画环境下，`.enter` 播完 220ms 后通过 `animationend` 事件自动移除，此后这行不再持有动画类。启用 `prefers-reduced-motion` 时 CSS 将动画设为 `none`，不会触发 `animationend`，因此类可能保留，但页面不会播放动画。若用户不刷新页面便关闭“减少动效”，这些旧行可能重新获得动画并播放一次；当前实现没有为这种运行时偏好切换增加定时清理兜底。

### 第三步：复用行靠 `dataset.id` 身份识别

`webui/static/render.js` `renderSection()`：

```js
function renderSection(section, items, ...) {
  // 用 dataset.id 建立现有 DOM 节点 Map
  const existing = new Map(
    [...section.list.querySelectorAll('.event-row')].map(node => [node.dataset.id, node])
  );

  const fragment = document.createDocumentFragment();
  for (const item of items) {
    const node = existing.get(item.id) || createEventRow(item);  // 命中→复用，miss→新建
    updateEventRow(node, item);
    fragment.append(node);
  }
  section.list.replaceChildren(fragment);
}
```

三步协同效果：

- **复用行**（`existing.get(item.id)` 命中）：在正常动画环境下已被 `animationend` 移除了 `.enter`，通过 `replaceChildren` 插回时不触发入场动画；
- **新建行**（`createEventRow`）：持有 `.enter`，插入 DOM 时播放 220ms 入场动画，播完自动移除；
- `replaceChildren` 仍会一次性写回该区段，但动画只发生在带 `.enter` 的行上。

这里的节点复用只发生在**同一个区段、同一个 ID** 内。`renderSection()` 分别为 done、running、pending 建立局部 Map；后端 ID 又分别带有 `done-`、`running-`、`pending-` 前缀。因此事件从 pending 进入 running、再进入 done 时会创建新节点，不是同一 DOM 节点跨区迁移。

### 为什么还用 `replaceChildren`

不换当然更好，但这里用 `replaceChildren` 有现实原因：列表的 DOM 顺序可能因新事件插入、排序变化而改变。`fragment` 按期望顺序 append 所有行，最后一口气替换，保证 DOM 顺序与数据一致，代码简单且不依赖 DOM 位置交换逻辑。

对于"旧行重复播放入场动画"这个问题，把动画限定在 `.enter` 上已经足够；这不代表 `replaceChildren` 对滚动锚定或其他浏览器状态没有影响。

### 补充：尊重用户动画偏好

`webui/static/styles.css` 末尾：

```css
@media (prefers-reduced-motion:reduce) {
  .event-row.enter, .running-section .section-marker span { animation:none; }
}
```

系统开启"减少动效"的用户不会看到任何入场动画。

## 二、下拉框重置

### 现象

旧实现中，用户在类型下拉框选择筛选条件（如只看 `qq` 事件）后，下一轮刷新可能回到"全部类型"，筛选失效。

### 根因

旧版 `refresh()` 每次成功拉取数据后都会调用 `populateTypes()`，该函数用 `replaceChildren` 替换所有 `<option>`。被选中的 option 随之被移除；如果重建后不显式恢复 `select.value`，选择会回到新 option 集合的默认项（这里是"全部类型"）。这不是 `value` 属性丢失，而是选中状态所属的 option 被替换。

### 修复（两处协同）

**第一处**：`populateTypes()` 保存并恢复选中值。

`webui/static/render.js`：

```js
export function populateTypes(select, items) {
  const selected = select.value;             // ← 1. 取出当前选中值，此时 DOM 还在
  const types = [...new Set(items.map(eventType))].sort(/*...*/);
  const fragment = document.createDocumentFragment();
  // ...重建所有 <option>...
  select.replaceChildren(fragment);
  select.value = types.includes(selected) ? selected : 'all';  // ← 2. 恢复；若原类型已不存在则回退 all
}
```

替换 options 后显式写回 `select.value`，可以恢复仍然存在的类型；若原类型已经不在新集合中，则有意回退到 `all`。

**第二处**：只在类型集合真的变了才重建。

`webui/static/app.js` `refresh()`：

```js
const oldTypes = state.snapshot ? new Set(state.snapshot.items.map(eventType)) : null;
const newTypes = new Set(snapshot.items.map(eventType));
const typesChanged = !oldTypes || oldTypes.size !== newTypes.size
                  || [...oldTypes].some((type) => !newTypes.has(type));
if (typesChanged) populateTypes(elements.typeFilter, snapshot.items);
```

类型集合不变（同一个 `event_type` 集合、大小相同、元素一致）时**完全不碰 DOM**。首次加载仍会调用 `populateTypes()`；此后只要类型集合不变就不再重建 options。类型集合变化时会调用它，但第一处修复会尽量保留当前选择。

> 第一处是"万一重建了也别丢选择"，第二处是"能不重建就不重建"。两层兜底。

## 三、滚动位置稳定

### 两类滚动状态

事件页存在两套彼此独立的滚动状态：

- `.timeline` 负责事件时间轴的页面级滚动；
- `.event-details pre` 设置了 `max-height` 和 `overflow:auto`，负责展开详情内部的滚动。

时间轴位置稳定不代表详情内部位置也稳定。排查滚动问题时必须先确认用户实际操作的是哪个滚动容器，再沿该容器的 DOM 生命周期检查 `scrollTop`，不能只观察外层页面。

### 当前 JS 做了什么

`renderSection()` 会按 `dataset.id` 复用同一区段中的行：

```js
const existing = new Map(
  [...section.list.querySelectorAll('.event-row')].map(node => [node.dataset.id, node])
);
```

旧实现随后按新数据顺序将节点放入 fragment：

```js
const node = existing.get(item.id) || createEventRow(item);  // 命中→复用，miss→新建
updateEventRow(node, item);
fragment.append(node);
```

这里曾有一个错误判断：同一 ID 确实复用了同一个 DOM 节点，能保留 `.expanded` 状态和按钮监听器，但 `fragment.append(node)` 会先把节点从当前文档中移走，最后 `replaceChildren(fragment)` 再插回列表。节点身份没变，不等于节点始终连接在文档中；可滚动的 `<pre>` 经历脱离和重新插入后，浏览器可能把内部 `scrollTop` 重置为 `0`。

当前实现改为原位 keyed reconciliation：从列表首节点开始逐项比较，同 ID、同顺序的行完全不移动；仅在新增、删除或换序时插入、移动或移除对应节点。这样普通轮询不会让已展开的详情容器脱离文档。

```js
let current = section.list.firstElementChild;
for (const item of items) {
  const node = existing.get(item.id) || createEventRow(item);
  updateEventRow(node, item);
  existing.delete(item.id);
  if (node === current) {
    current = current.nextElementSibling;
  } else {
    section.list.insertBefore(node, current);
  }
}
```

`updateEventRow()` 也不再每轮无条件写入详情文本。只有 JSON 内容确实变化时才更新 `textContent`，并在更新前后保存、恢复详情自身的 `scrollTop`：

```js
const details = row.querySelector('pre');
const content = JSON.stringify(item.event, null, 2);
if (details.textContent !== content) {
  const scrollTop = details.scrollTop;
  details.textContent = content;
  details.scrollTop = scrollTop;
}
```

### 方案边界

- 普通轮询只更新内容或复用现有行，不会主动修改页面滚动位置；
- 新 pending 行位于等待区底部，不改变它上方内容的位置；
- pending、running、done 之间迁移时 ID 和所属列表都会变化，因此会创建新节点；迁移瞬间的详情展开状态和内部滚动位置不保证跨状态继承；
- 用户主动展开详情会改变页面高度，这是交互本身的预期结果，不属于轮询导致的滚动丢失。

### 已落地补偿

当前页面在每次重新渲染事件列表前，会先记住当前视口中最靠近顶部的事件行及其相对偏移。渲染完成后（同帧绘制前）再把同一条行恢复到相同的可视位置，因此新事件进入时不会把正在看的事件整体“顶上去”。这条补偿逻辑在 `webui/static/app.js` 与 `webui/static/scroll-anchor.js` 中生效，适用于普通轮询、筛选变化和区段内容重排的场景。

补偿与“回到正在执行”按钮的协作：JS 写 `scrollTop` 会取消浏览器正在进行的平滑滚动，因此点击按钮后会设置约 1.2 秒的抑制窗口（`anchorRestoreSuppressedUntil`），窗口内跳过锚点恢复，保证平滑滚动不被中途打断；抑制检查在渲染时和 `requestAnimationFrame` 回调执行前各做一次。锚点查找使用 `CSS.escape`，避免未来 ID 格式变化导致选择器异常。若筛选导致锚点行消失，则退化为保持原 `scrollTop`。

### 锚定实现的要点与教训

1. **JS 写 `scrollTop` 会取消正在进行的平滑滚动**。锚点恢复与“回到正在执行”按钮天然冲突，必须设抑制窗口跳过恢复；且仅在渲染时检查不够——检查通过到 rAF 回调执行之间仍有一帧间隙，回调执行前必须再查一次。
2. **拼接选择器时用 `CSS.escape`**，即使当前 ID 字符集安全（后端指纹为 base36），也不要依赖这个假设。
3. **恢复时机放在 rAF 回调（绘制前）**，`scrollTop` 纠正与新内容同帧完成，视觉上无跳动。
4. **锚点行可能消失**（被筛选掉），此时应退化为保持原 `scrollTop`，不做任何恢复。
5. **节点复用不等于节点未脱离文档**。`DocumentFragment.append()` 会移动已有节点；需要保留输入焦点、文本选择或内部滚动位置时，应优先原位更新 DOM。
6. **避免无条件设置 `textContent` 或 `innerHTML`**。即使最终字符串相同，重复写入也可能重建文本节点并扰动选择、滚动等浏览器状态；先比较内容，再决定是否写入。
7. **外层锚点补偿不能修复内层滚动容器**。每个带 `overflow:auto` 或 `overflow:scroll` 的元素都有独立 `scrollTop`，测试时应分别记录刷新前后的值。
8. **不要仅凭代码阅读宣告滚动问题已解决**。最低限度应展开一个超过 `max-height` 的详情，滚动到中部，跨越多次自动刷新，并确认详情节点仍连接在文档中且 `scrollTop` 不变；还要覆盖详情内容变化和事件状态迁移两个边界场景。

## 四、可复用经验

处理轮询刷新导致的 UI 状态丢失，可按以下顺序排查：

1. **先定位状态所有者**：滚动、焦点、选区、展开状态分别属于哪个具体 DOM 节点，不要把外层页面状态与内层控件状态混为一谈。
2. **再检查节点生命周期**：确认刷新前后是否为同一节点，以及节点是否始终留在文档中；“对象被复用”不代表“从未被搬走”。
3. **减少 DOM 写入**：数据未变化时不更新 DOM；确需更新时优先原位修改，避免整段替换。
4. **必要时显式保存状态**：内容变化不可避免时，在写入前读取状态，写入后恢复，并为节点删除或身份变化准备退化路径。
5. **用真实交互验证**：让目标控件进入非默认状态，跨越多次刷新，直接比较刷新前后的节点身份、连接状态和状态值。

核心原则：**稳定 UI 的关键不是“刷新后补回多少状态”，而是尽量不破坏浏览器已经维护好的状态。**

## 五、全局终端

### 5.1 历史投影

终端页定位为全局追加式终端，不再尝试表达一问一答的对话关系：

- 写入端将 `webui` 事件通过 `RPUSH` 放到 Redis List 的消费端，获得与内部连续性事件相同的最高队列优先级；
- 读取端只查询 MongoDB 中已经消费并落库的 `webui` 和 `response` 事件，不读取 Redis pending 或 Worker running 状态；
- 前端按 MongoDB `_id` 的历史顺序追加事件，同一个 `_id` 只渲染一次；
- 提交成功后不立即乐观渲染，只有 Worker 消费并写入 MongoDB 后，命令才会出现在终端中；
- `webui` 与 `response` 不做配对。当前事件没有 `conversation_id`、`correlation_id` 或 `causation_id`，而 `response` 也可能由 QQ 或其他入口触发，任何基于邻接、时间或内容的归属推断都不可靠。

该方案把 Redis 限定为调度层、MongoDB 限定为终端读模型，消除了跨存储去重和状态迁移问题。代价是 `RPUSH` 的终端命令会与 `active`、`tool`、`response` 等内部连续性事件竞争队尾：新终端命令可能插入尚未消费完的工具链。若以后要求工具链原子连续，应改为独立优先队列或显式优先级结构，而不是继续共用同一个 Redis List 的 `RPUSH` 端。

### 5.2 终端命名统一

原 WebUI `Chat` 功能已经完整迁移为“终端”/`terminal`：

- 页面和脚本入口改为 `/terminal.html` 与 `/terminal.js`；
- HTTP 接口改为 `GET /api/terminal/history` 和 `POST /api/terminal`；
- Go、JavaScript、DOM ID 和 CSS class 中属于该页面的 `chat` 标识统一改为 `terminal`；
- 导航和页面可见文案统一显示“终端”或 `TERMINAL`；
- 事件协议仍使用 `event_type: "webui"`，没有引入新的 `terminal` 事件类型。

这里的命名迁移只针对 WebUI 页面功能，不影响 Python LLM 业务中的 `chat_with_deepseek()` 或模型服务的 `chat/completions` 概念。

### 5.3 导航与刷新状态

事件页和终端页使用同一套顶栏控制：

- 页面导航；
- 自动刷新间隔；
- 暂停或继续自动刷新；
- 手动立即刷新；
- 最后同步时间；
- 自动刷新状态。

独立的“已同步”状态被删除，避免与最后同步时间重复。同步过程和异常直接占用时间位置，分别显示“同步中”“同步超时”或“同步失败”。移动端顶栏使用双层布局，减少导航、同步信息和刷新控件之间的重叠。

### 5.4 消息气泡视觉方向

终端命令位于右侧，Agent 响应位于左侧。两类气泡的强调描边放在消息列表的外侧：

- 右侧 `TERMINAL` 命令使用右侧绿色重描边；
- 左侧 `AGENT` 响应使用左侧蓝色重描边；
- 两个朝向列表中间的边保持普通细描边。

旧方向把两条重描边都放在中间侧，会在阅读区形成明显分割。移到外侧后仍能表达来源和方向，同时保持中间消息流连续。

### 5.5 首次定位与增量滚动

终端首次拉取历史时会一次追加最近窗口内的所有消息。若首批历史也使用平滑滚动，用户每次打开页面都会看到视口从顶部移动到最底部，历史越长等待感越明显。

当前通过 `historyLoaded` 区分首次加载与后续增量：

```js
behavior: state.historyLoaded ? 'smooth' : 'auto'
```

- 首次历史加载完成后直接定位到列表底部，不播放长距离滚动；
- 后续轮询追加新消息时保留平滑滚动；
- 首次请求失败不会错误地把历史标记为已加载，成功取得历史后仍使用即时定位。

### 5.6 “跳到最新”按钮

终端标题栏增加了“跳到最新”按钮，视觉样式参考事件页的“回到正在执行”按钮。它同时承担位置跳转和新消息提示：

1. 首次加载历史不点亮按钮；
2. 首次加载后的轮询追加新 ObjectID 时，只有用户不在底部才增加 `.has-updates` 并显示绿色；
3. 点击按钮会平滑滚动到 `messageList.scrollHeight`，并清除绿色状态；
4. 用户停留在列表底部时，新消息仍自动平滑滚动到最新位置；
5. 用户向上查看历史时，新消息只点亮按钮，不强制改变当前阅读位置。

是否自动跟随由追加前的距离判断决定：

```js
const remaining = messageList.scrollHeight - messageList.scrollTop - messageList.clientHeight;
const wasNearBottom = remaining <= 24;
```

必须在插入新节点前计算 `wasNearBottom`。如果插入后才计算，新增内容已经增加了 `scrollHeight`，原本位于底部的用户会被误判为离开底部。只有 `state.historyLoaded && !wasNearBottom` 时才添加 `.has-updates`，因此正在跟随最新消息的用户不会看到多余的绿色提示。

按钮仍绑定消息列表的 `scroll` 事件：当用户手动向下滚回距离底部 24px 以内时，立即移除 `.has-updates`。点击按钮也会先清除状态，再平滑滚动到底部。这样绿色状态表达的是“用户当前没有跟随最新消息”，而不是“最近发生过刷新”；程序自动滚动到达底部时也会通过同一规则清除状态。

### 5.7 当前边界

- “跳到最新”的绿色状态表达“存在新消息且用户当前没有跟随底部”，不是严格的可视区未读计数；
- 用户本来就在底部并自动看到新消息时，按钮保持普通颜色；用户手动滚回底部时，绿色状态自动清除；
- 终端仍使用固定窗口轮询。若单次新增数量超过历史接口窗口，窗口外事件无法由当前页面补回；
- 当前改动经过 HTML、CSS 和 JavaScript 静态诊断，运行时滚动手感仍应在实际容器尺寸和移动端视口下复核。
