# WebUI 轮询刷新优化记录

> 2026-07-31，2026-08-01 按当前实现复核。WebUI 默认每 2s 轮询一次，也可选择 1s、5s 或 10s。本文记录列表动画和类型筛选的已落地优化，并说明当前实现对滚动位置的实际保证。完整事件流设计见[前端事件流设计](前端事件流设计.md)。

## 一、列表闪烁

旧实现中，每轮轮询时整个事件列表会"闪"一下。轮询频率会影响出现次数，但不是动画重播的直接原因。

### 根因

三条代码合谋造成的：

1. **CSS**：入场动画原本挂在 `.event-row` 选择器上，每行都有 `animation:reveal 220ms`
2. **JS**：`renderSection()` 每轮都执行 `section.list.replaceChildren(fragment)`，整表重建
3. **浏览器行为**：持有动画样式的节点被移出文档再插回后，动画可能重新开始

当前渲染流程会先把已有节点 `append` 到 `DocumentFragment`，再调用 `replaceChildren` 写回列表。若所有 `.event-row` 都永久持有入场动画，这种移出再插回会让动画重复出现；轮询返回的行越多，视觉闪烁越明显。

### 修复（三步）

### 第一步：动画从行选择器移到独立 class

`webui/static/styles.css`：

```css
/* 原来：动画挂在行上，每行都有 */
.event-row { animation:reveal 220ms ease both; }

/* 修复：动画只属于 .enter，复用行不持有 */
.event-row.enter { animation:reveal 220ms ease both; }
```

`@keyframes reveal` 不变：

```css
@keyframes reveal {
  from { opacity:0; transform:translateY(4px); }
  to   { opacity:1; transform:translateY(0); }
}
```

### 第二步：新建行加 `.enter`，播完即删

`webui/static/render.js` `createEventRow()`：

```js
function createEventRow(item) {
  const row = document.createElement('article');
  row.className = 'event-row';
  row.dataset.id = item.id;
  row.classList.add('enter');                                             // ← 只有新建行
  row.addEventListener('animationend', () => row.classList.remove('enter'), { once: true });
  // ...innerHTML 填充...
}
```

正常动画环境下，`.enter` 播完 220ms 后通过 `animationend` 事件自动移除，此后这行不再持有动画类。启用 `prefers-reduced-motion` 时 CSS 将动画设为 `none`，不会触发 `animationend`，因此类可能保留，但页面不会播放动画。

### 第三步：复用行靠 `dataset.id` 身份识别

`webui/static/render.js` `renderSection()`：

```js
function renderSection(section, items, ...) {
  // 用 dataset.id 建立现有 DOM 节点 Map
  const existing = new Map(
    [...section.list.querySelectorAll('.event-row')].map(node => [node.dataset.id, node])
  );

  const fragment = document.createDocumentFragment();
  for (const item of items) {
    const node = existing.get(item.id) || createEventRow(item);  // 命中→复用，miss→新建
    updateEventRow(node, item);
    fragment.append(node);
  }
  section.list.replaceChildren(fragment);
}
```

三步协同效果：

- **复用行**（`existing.get(item.id)` 命中）：已被 `animationend` 移除了 `.enter`，通过 `replaceChildren` 插回时**不触发任何动画**；
- **新建行**（`createEventRow`）：持有 `.enter`，插入 DOM 时播放 220ms 入场动画，播完自动移除；
- `replaceChildren` 仍会一次性写回该区段，但动画只发生在带 `.enter` 的行上。

这里的节点复用只发生在**同一个区段、同一个 ID** 内。`renderSection()` 分别为 done、running、pending 建立局部 Map；后端 ID 又分别带有 `done-`、`running-`、`pending-` 前缀。因此事件从 pending 进入 running、再进入 done 时会创建新节点，不是同一 DOM 节点跨区迁移。

### 为什么还用 `replaceChildren`

不换当然更好，但这里用 `replaceChildren` 有现实原因：列表的 DOM 顺序可能因新事件插入、排序变化而改变。`fragment` 按期望顺序 append 所有行，最后一口气替换，保证 DOM 顺序与数据一致，代码简单且不依赖 DOM 位置交换逻辑。

对于"旧行重复播放入场动画"这个问题，把动画限定在 `.enter` 上已经足够；这不代表 `replaceChildren` 对滚动锚定或其他浏览器状态没有影响。

### 补充：尊重用户动画偏好

`webui/static/styles.css` 末尾：

```css
@media (prefers-reduced-motion:reduce) {
  .event-row.enter, .running-section .section-marker span { animation:none; }
}
```

系统开启"减少动效"的用户不会看到任何入场动画。

## 二、下拉框重置

### 现象

旧实现中，用户在类型下拉框选择筛选条件（如只看 `qq` 事件）后，下一轮刷新可能回到"全部类型"，筛选失效。

### 根因

旧版 `refresh()` 每次成功拉取数据后都会调用 `populateTypes()`，该函数用 `replaceChildren` 替换所有 `<option>`。被选中的 option 随之被移除；如果重建后不显式恢复 `select.value`，选择会回到新 option 集合的默认项（这里是"全部类型"）。这不是 `value` 属性丢失，而是选中状态所属的 option 被替换。

### 修复（两处协同）

**第一处**：`populateTypes()` 保存并恢复选中值。

`webui/static/render.js`：

```js
export function populateTypes(select, items) {
  const selected = select.value;             // ← 1. 取出当前选中值，此时 DOM 还在
  const types = [...new Set(items.map(eventType))].sort(/*...*/);
  const fragment = document.createDocumentFragment();
  // ...重建所有 <option>...
  select.replaceChildren(fragment);
  select.value = types.includes(selected) ? selected : 'all';  // ← 2. 恢复；若原类型已不存在则回退 all
}
```

替换 options 后显式写回 `select.value`，可以恢复仍然存在的类型；若原类型已经不在新集合中，则有意回退到 `all`。

**第二处**：只在类型集合真的变了才重建。

`webui/static/app.js` `refresh()`：

```js
const oldTypes = state.snapshot ? new Set(state.snapshot.items.map(eventType)) : null;
const newTypes = new Set(snapshot.items.map(eventType));
const typesChanged = !oldTypes || oldTypes.size !== newTypes.size
                  || [...oldTypes].some((type) => !newTypes.has(type));
if (typesChanged) populateTypes(elements.typeFilter, snapshot.items);
```

类型集合不变（同一个 `event_type` 集合、大小相同、元素一致）时**完全不碰 DOM**。首次加载仍会调用 `populateTypes()`；此后只要类型集合不变就不再重建 options。类型集合变化时会调用它，但第一处修复会尽量保留当前选择。

> 第一处是"万一重建了也别丢选择"，第二处是"能不重建就不重建"。两层兜底。

## 三、滚动位置稳定

### 验证结果

实际持续轮询验证中，页面没有发生错误滚动或刷新后跳回顶部的问题。当前页面由 `body` 承担页面级滚动，`#historyList`、`#runningList`、`#pendingList` 没有设置 `overflow` 或固定高度，因此不存在三个列表各自重置 `scrollTop` 的问题。

### 当前 JS 做了什么

`renderSection()` 会按 `dataset.id` 复用同一区段中的行：

```js
const existing = new Map(
  [...section.list.querySelectorAll('.event-row')].map(node => [node.dataset.id, node])
);
```

然后按新数据顺序将节点放入 fragment：

```js
const node = existing.get(item.id) || createEventRow(item);  // 命中→复用，miss→新建
updateEventRow(node, item);
fragment.append(node);
```

同一 ID 的行是同一个 DOM 节点。这能保留节点上的 `.expanded` 状态和按钮监听器，也避免无意义地重新创建整行。三个区段始终保留，空闲时也会渲染固定的空状态，因此普通轮询不会反复拆装页面主体结构。

当前代码没有读取或恢复 `window.scrollY`，也没有记录视口中的锚点元素。滚动稳定来自页面级滚动、区段结构稳定、同 ID 节点复用，以及浏览器自身的滚动锚定。按当前数据规模和单 Worker 逐条推进的更新方式，实测已经满足体验要求，因此不需要额外加入滚动补偿逻辑。

### 方案边界

- 普通轮询只更新内容或复用现有行，不会主动修改页面滚动位置；
- 新 pending 行位于等待区底部，不改变它上方内容的位置；
- pending、running、done 之间迁移时会更换节点，但当前逐条迁移未造成可见的错误滚动；
- 用户主动展开详情会改变页面高度，这是交互本身的预期结果，不属于轮询导致的滚动丢失。

如果未来在批量导入、大幅调整区段高度等新场景中出现可稳定复现的视口偏移，再考虑记录可见事件 ID 及其视口坐标，并在渲染后通过 `window.scrollBy()` 补偿。现阶段不引入这段复杂度。
