# 09 工具消息格式

> 回答一个问题:**工具的调用与结果,以什么格式进入 LLM 上下文,为什么是这样?**
> 涉及代码:`agent/llm.py` 的 `chat_with_deepseek()`。

## 1. 背景:为什么"格式"值得单独成文

系统把 LLM 上下文建立在 MongoDB 事件历史的"最近 N 条"之上(当前 N=10)。工具链事件(`response → tool → tool_return`)天然成组出现,而截断窗口可能恰好落在组内:

- 保留了 `assistant(tool_calls)` 却丢了它的工具结果;
- 或者留下了孤悬的工具结果,却没有对应的 `assistant(tool_calls)`。

OpenAI 兼容 API 对这两种序列都会返回 400,一轮对话直接失败,且失败发生在上下文组装阶段、无法通过重试当前请求修复。

## 2. 方案:不用 `tool` 角色,全文本投影

`chat_with_deepseek()` 中只有三条映射规则:

| 历史事件 | 上下文角色 | 内容 |
|----------|-----------|------|
| `qq` | `user` | `<groupmsg group=... sender=...>...</groupmsg>` 或 `<privatemsg sender=...>...</privatemsg>` |
| `tool_return` | `user` | `Tool {tool} args({json.dumps(args)}) result: {result}` |
| `response` | `assistant` | `payload["content"]` |

关键取舍,两点缺一不可:

1. `tool_return` 不使用原生 `tool` 角色,而是折叠成 `user` 文本;
2. `response` 不再携带 `tool_calls` 字段。

于是消息序列中**不存在任何配对约束**,截断天然免疫——这是本方案的全部意义。前一轮尝试过的"成对截断"方案(逐条扫描补全消息对)逻辑繁琐、边界情况多,被本方案取代。

## 3. 追溯证据链:为什么不丢信息

改用 `user` 文本**不等于丢失信息**。证据链由两层保证:

- **权威层(结构化存档)**:MongoDB 的 `tool_return` 事件始终保留完整的结构化数据(`id` / `tool` / `args` / `result` / `success` / `created_at`),这是可追溯的证据源头,任何时刻都可以按 `payload.id` 检索;
- **投影层(LLM 上下文)**:把同一份数据折叠为 `Tool {tool} args({args}) result: {result}`,模型在推理时能看到"调用了什么工具、传入什么参数、得到什么结果"的完整闭环。

即:**上下文是证据链的文本投影,MongoDB 是证据链的结构化存档**。两者内容一致、只是形态不同——"追溯"不被打断靠的是这份一致性,而不是 `tool_call_id` 的协议配对。

## 4. 方案对比

| 方案 | 做法 | 截断安全性 | 证据链 | 复杂度 |
|------|------|-----------|--------|--------|
| 原生 `tool` 角色 | `tool_return` → `tool`,`tool_call_id` 配对 | 差,截断即 400 | 结构化,但依赖配对 | 需成对截断兜底,复杂 |
| 丢弃工具结果 | `tool_return` 不进上下文 | 安全 | 断裂,模型不知道工具执行过 | 极简,但不可用 |
| **本方案(已采用)** | `tool_return` → `user` 文本,`response` 去 `tool_calls` | 天然安全 | 完整:工具名 + 参数 + 结果 | 三条映射规则 |

## 5. 代价与已知边界

- **丢失 `tool_call_id` 的结构化关联**:模型无法精确引用"第 N 次工具调用",但对当前文本型工具(余额、搜索)无影响;需要时仍可从 MongoDB 按 `payload.id` 检索;
- **工具轮的 `assistant` 消息 content 通常为空**:当前实现会写入 content 为空的 `assistant` 消息,各兼容 API 接受空字符串;若未来某模型拒绝,可在此处补 `(调用工具)` 占位;
- **隐式 `json` 依赖(技术债)**:`chat_with_deepseek()` 使用了 `json.dumps`,但 `llm.py` 没有显式 `import json`,靠的是 `from tool import *` 隐式导出了 `tool.py` 顶部的 `import json`。建议后续补上显式 `import json`(见 08 优化报告 S1)。
