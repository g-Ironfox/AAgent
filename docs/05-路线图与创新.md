## 1. 当前已经实现

### 1.1 单一决策中心与线性推进

**状态:已实现**

系统目前由单个 `agent` worker 消费统一 Redis 队列,同步处理事件。LLM 调用、模型响应写回、工具执行和工具结果写回都在同一条事件时间线上推进。

它解决的是上下文并发写入造成的决策分叉问题:新的外部消息可以进入队列,但不会在当前 LLM 调用或工具链完成前抢占执行。

### 1.2 事件统一记录管线

**状态:已实现**

所有事件进入 worker 后都会先调用 `record_history()` 写入 MongoDB,再根据 `event_type` 执行后续逻辑。`response` 和 `tool_return` 不是额外建立的历史机制,而是通过新增事件类型直接复用已有记录管线。

同一份记录因此同时服务于:

- 事件审计;
- LLM 上下文组装;
- WebUI 历史监控;
- 工具调用追踪;
- 后续 document 召回的基础数据。

这是 AAgent 的“一鱼多吃”:通过统一事件记录获得多个用途,而不是为每个用途维护一份互相漂移的数据。

### 1.3 Redis List 的双重职责

**状态:已实现**

Redis List 同时负责外部任务的普通排队和内部连续性事件的优先处理:

- `LPUSH` + `BRPOP`:外部事件普通排队;
- `RPUSH` + `BRPOP`:工具链和 LLM 内部事件优先处理。

因此,同一个队列既承担顺序编排,也承担入口流量缓冲。这个机制已经用于 `qq`、`active`、`response`、`tool` 和 `tool_return` 事件。

### 1.4 事件源与执行核心分离

**状态:已实现**

QQ 和 WebUI 均已作为独立事件源接入统一队列,各自产生 `qq` / `webui` 事件。agent 不直接依赖 QQ WebSocket 或 HTTP 来推进状态,所有事件先写入 MongoDB 历史,LLM 从历史中 callback 所需信息(`active` 事件不再携带 `user_id`/`group_id`/`message`)。

WebUI 已实现事件流首页(pending / running / done 三区段)与全局终端页(仅展示 MongoDB 已消费的 `webui` / `response` 历史,按 `_id` 追加去重)。

## 2. 规划中的创新方向

### 2.1 全局信息的 Document Callback

**状态:规划中,尚未实现**

当前 `llm.py` 只读取最近 10 条事件。未来计划把事件和其他信息组织成带有来源、时间、主题、实体和任务等元数据的 document,再根据当前任务按相关性召回,组成 LLM 的当前工作集。

这不是按用户或会话复制多份历史,而是从同一个全局信息空间进行按需投影。召回不保证天然完整,召回策略、document 结构和元数据设计本身就是系统需要承担的设计责任。

拟人化地说:

> 如果认为全局 callback 会召回不全,将心比心地对于人类来说,也只能责怪当初的自己思虑不周了。

### 2.2 Skill-Tool 能力封装

**状态:规划中,尚未实现**

未来计划把装备专门 skill 的 LLM 封装成主 Agent 可调用的 tool。主 Agent 只接收结构化结果,不必把专门领域的全部说明、流程和中间过程长期塞进主上下文。

它的创新点在于把“专门能力”放进工具边界,但不把最终决策权拆出去。Skill-Tool 可以复杂,主 Agent 仍然只有一个。

### 2.3 空闲时钟事件

**状态:规划中,尚未实现**

当前系统由外部消息或工具链事件推动。未来可以在队列空闲时提交周期性的检查、计划和提醒事件,让 Agent 具备主动行为。

时钟只负责产生事件,不直接启动后台 LLM 分支。所有主动行为仍然要回到统一队列和单 worker 的线性执行模型中。

### 2.4 WebUI Chat 回复展示

**状态:部分实现,尚未完成**

当前 Chat 页面已支持提交消息到 Agent 队列,但只能看到"已入队"的用户消息。后续需要让 Chat 页面能够回显 Agent 的最终 `response`,并展示工具调用过程。

### 2.5 异步任务兼容

**状态:规划中,尚未实现**

严格同步约束针对的是主 Agent 的思考、上下文写回和状态推进,不是所有外部任务都必须同步阻塞。对于耗时较长、收益不足以阻塞主 Agent、且结果可预测或结果格式可预先约定的任务,未来可以兼容异步工具 API。

该设计不允许异步任务开辟第二条 Agent 推理时间线。它只定义一个可追踪的等待协议:

1. `async_request`:发布异步任务,记录任务 ID、任务类型、参数、发布来源和预期结果格式,并把“任务已发布但结果尚不确定”写入上下文;
2. 外部异步工具执行任务,完成时间可以晚于当前推理,但不能直接修改 Agent 状态或调用 LLM;
3. `async_result`:异步工具完成后将任务 ID、结果或错误信息回推 Redis List;
4. 单 worker 消费并记录 `async_result`,再按任务协议排入后续 `active` 事件,由新的 LLM 调用使用结果。

主 Agent 必须知道等待的存在,也必须知道结果尚未确定。未收到 `async_result` 之前,模型只能把该任务视为待完成事项,不能把预期结果当成事实。该机制是“兼容异步任务”,不是“允许异步思考”。

### 2.6 MCTS 发散式探索

**状态:保留方向,尚未实现**

未来可以尝试引入 MCTS,让 Agent 针对一个问题发散出多个可能路径,再比较这些路径,尝试寻找更优解。它与当前单一决策中心并不矛盾:探索过程可以是主 Agent 的受控规划阶段,最终仍由同一个决策中心选择方案并写回权威上下文。

MCTS 的主要限制是计算、模型调用和工具执行开销。探索宽度、深度、评估次数和可用预算都需要受到约束,否则寻找更优解的收益可能抵不过额外成本。具体算法、触发条件和预算策略暂不确定,以后再继续设计。

未来会尝试引入交叉验证,用于比较不同探索路径在不同任务样本或评估条件下的稳定性,避免 MCTS 只在单一场景中得到看似更优但泛化性不足的结果。

### 2.7 Workflow-Tool:从能力封装到流程封装

**状态:规划中,尚未实现**

Skill-Tool 把专门能力封装进工具边界,让主 Agent 只接收结构化结果。但如果再往前推一步:很多复杂任务本身就可以由多个 Skill-Tool 按一定顺序、条件和分支组织而成。这些"由 Skill-Tool 编排而成的流程"如果足够稳定、足够通用,是否也应该被封装成一种新的工具?

这就是 Workflow-Tool 的核心思路:

> Skill-Tool 封装的是**能力**,Workflow-Tool 封装的是**流程**。

具体来说:

1. **定义层**:Workflow-Tool 是一个声明式的流程定义,描述若干 Skill-Tool 之间的调用顺序、条件分支、并行/串行关系和失败回退策略。它不引入新的原子能力,只编排已有能力。
2. **调用层**:对主 Agent 而言,Workflow-Tool 与普通 tool 或 Skill-Tool 没有区别——接收参数,返回结构化结果。内部的 multi-step 编排对主 Agent 完全透明。
3. **复用层**:一旦某个 workflow 被验证为稳定可靠,它就可以跨任务、跨会话复用,甚至在不同 Agent 之间共享。

它与 Skill-Tool 的关系不是替代,而是层级递进:

```
原子 Tool → Skill-Tool(封装专门能力)
Skill-Tool × N → Workflow-Tool(封装流程编排)
```

一个直观的类比:原子 Tool 是函数,Skill-Tool 是模块,Workflow-Tool 是管道(pipeline)。主 Agent 不需要知道管道内部有多少个模块在协作,只需要知道"这个管道能完成什么任务"。

Workflow-Tool 不打破单一决策中心原则。Workflow 内部是确定的、预定义的编排逻辑,不是第二条 Agent 推理时间线。它只是在工具层面做了更高层的抽象,把"怎么做一件事"的流程知识从主 Agent 的上下文里移到了可复用的工具定义里。

拟人化地说:

> 如果你发现自己反复教 Agent 同样的做事步骤,那这些步骤就不应该留在 prompt 里,而应该变成一个 Workflow-Tool。

### 2.8 Skill-Tool 的遗传算法优化:控制变量法的自动化

**状态:规划中,尚未实现**

Skill-Tool 一旦落地,马上会面临一个现实问题:同一个 skill 换个 prompt、换个温度、换个模型、换套工具组合,表现可能天差地别。手工调参不仅低效,而且容易陷入局部最优——你试了三组参数,选了最好的那个,但可能第四组会更好。

遗传算法(Genetic Algorithm, GA)为这个问题提供了一条系统化的路径:

**核心思路**:把每个 Skill-Tool 的配置视为一个"个体",配置项(系统 prompt、temperature、模型选择、工具子集、上下文窗口策略等)视为"基因"。通过"种群 → 评估 → 选择 → 交叉 → 变异"的迭代,自动寻找最优配置组合。

具体设计:

1. **基因编码**:每个 Skill-Tool 的可调配置项编码为一个基因组。离散型基因(如模型选择)用类别编码,连续型基因(如 temperature)用实数值编码,文本型基因(如 system prompt 的关键段落)用模板+参数的方式编码。
2. **适应度函数**:在标准化 benchmark 任务集上运行每个个体,综合评分。适应度可以多维度:任务完成率、响应质量(由评判 LLM 打分)、token 效率、平均延迟等,加权合成总分。
3. **控制变量法嵌入**:GA 的每一代不是盲目变异所有基因。可以在代际之间采用控制变量策略——锁定一批基因,只变异另一批,观察适应度变化的归因。这样既能加速收敛,又能产出可解释的结论("这个 skill 的瓶颈在 temperature 而不是 prompt 设计")。
4. **精英保留与多样性**:每代保留 top-K 个体直接进入下一代,同时通过变异和交叉维持种群多样性,避免过早收敛到局部最优。
5. **终止条件**:适应度收敛、达到预设代数上限、或连续 N 代无显著提升时终止。

这个方案的精妙之处不在于 GA 本身(那是成熟技术),而在于把它用在 Skill-Tool 这个抽象层上:

- **优化对象不是单个 prompt,而是一个封装好的能力单元。** 这意味着优化结果可以独立验证、独立部署、独立回滚。
- **控制变量法的嵌入让优化过程可解释。** 不是黑盒产出一个"更好的配置",而是能告诉你哪个配置项对结果影响最大。
- **benchmark 任务集可以持续积累。** 每发现一个 corner case,就加入 benchmark,让后续所有 skill 的优化都自动覆盖这个场景。

它与 Workflow-Tool 还有一层配合关系:当 Workflow-Tool 编排多个 Skill-Tool 时,可以先用 GA 分别优化每个子 Skill,再把优化后的配置组合进 Workflow,最后对 Workflow 整体做端到端验证。这样优化是分层、可组合的。

拟人化地说:

> 手工调 prompt 像是在调收音机的旋钮,遗传算法优化像是在用信号发生器扫频——你不只是在找一个能听的台,你是在绘制整个频段的响应曲线。

### 2.9 ReAct + RAG 协同与潜意识搜索

**状态:规划中,尚未实现**

ReAct 和 RAG 并不互斥,它们解决的是不同问题,可以在同一个 Agent 中互相补充:

- **ReAct** 负责显式的行动循环:Agent 根据当前上下文进行推理,选择工具或行动,观察结果,再决定下一步;
- **RAG** 负责显式的信息召回:根据当前任务从全局 document 信息空间中检索相关材料,注入当前工作集;
- **潜意识搜索** 负责后台的信息补充:在不打断主 Agent 当前决策链的前提下,根据任务主题、实体、未决问题或可能的信息缺口,提前搜索并准备候选 document。

三者可以形成互补关系:

```text
潜意识搜索:后台发现可能相关的信息
	↓
RAG:按当前任务筛选并召回相关信息
	↓
ReAct:基于上下文和工具观察进行显式决策
	↓
新的信息缺口:触发下一轮潜意识搜索
```

这里的“潜意识”不是脱离系统控制的第二个 Agent,也不是偷偷修改主 Agent 状态的后台推理分支。它更适合被定义为一种受约束的信息预取机制:

1. 主 Agent 或已有事件产生搜索主题、实体、未决问题等线索;
2. 潜意识搜索根据预算和优先级异步生成候选 document 或检索索引;
3. 候选结果先进入可追踪的暂存区,不能直接成为事实,也不能直接改写权威上下文;
4. 主 Agent 下一次 RAG 召回时,统一评估这些候选信息的相关性、来源和时效性;
5. 只有被显式召回并通过上下文组装规则的信息,才能参与 ReAct 的下一轮决策。

这样设计可以兼顾两种需求:ReAct 保持行动过程的可观察性和可解释性,RAG 保持上下文的相关性,潜意识搜索则负责降低“当前召回范围之外存在重要信息”这一风险。潜意识搜索的产物始终是候选材料,而不是未经验证的记忆或结论。

该方向需要重点约束搜索预算、触发条件、去重策略、来源标注、结果过期时间和失败处理,避免后台搜索带来无边界的工具调用或隐式状态变化。

### 2.10 Git 式思考分支与语义合并

**状态:规划中,尚未实现**

AAgent 主打“一条上下文”和单一决策中心,但“一条权威主线”不等于“不能暂时保留多个思考候选”。可以借鉴 Git 的历史版本控制,允许 Agent 从某个历史事件或上下文版本创建思考分支,在分支中探索不同假设、方案或工具路径,再把没有冲突的有效结论合并回主线。

这里的 branch 不是第二个永久运行的 Agent,也不是绕过单 worker 的并发写入。它更准确地说是一个带父版本的**候选上下文快照**:

1. `branch_create`:记录父事件、父上下文版本、创建原因、创建者和预算,生成一个独立的候选 head;
2. 分支事件:所有推理草稿、工具结果和中间结论都带有 `branch_id` 与 `parent_event_id`,写入统一历史,但默认不进入主线 callback;
3. 分支评估:对分支的目标、证据、工具副作用、成本和结论质量进行评估,形成可合并的候选变更;
4. `branch_merge`:以主线当前版本、分支父版本和分支 head 做三方合并,生成一个新的 merge event,而不是直接覆盖已有历史;
5. 合并后的结果再次由单一决策中心确认并写入权威上下文。未合并的分支仍然保留,可以继续探索、比较或废弃。

“不冲突”不能只理解为两段文本没有重复。合并至少需要区分三种情况:

- **事实不冲突**:两条分支引用了相容的证据或分别补充了不同信息,可以自动合并;
- **结论不冲突**:两条分支得出的建议可以同时成立,但仍需保留来源、置信度和适用条件;
- **决策冲突**:修改了同一目标、依赖互斥事实、产生相反行动或工具副作用,必须保留冲突标记,交给主 Agent 或人类处理,不能静默选一边。

因此,合并对象不应只是自然语言文本,而应尽量表示为带来源的结构化候选变更,例如事实、假设、计划、决策、未决问题和工具副作用。自动合并只能处理具有明确可组合语义的变更;对于无法判定的内容,宁可产生冲突也不能伪造“无冲突”。

该机制带来几个收益:

- 可以在不污染主上下文的情况下比较不同时间点、不同假设下的思考;
- 可以复用 Git 式的回溯、分叉、比较、合并和废弃语义;
- 可以把 MCTS、候选方案比较和 draft-review 统一为分支上的可追踪操作;
- 合并事件天然形成审计记录,能够解释“主线为什么采用了这部分结论”。

同时必须保持几个不变量:

- 主线只能由单 worker 按版本校验顺序推进,分支不能直接修改主线;
- 合并必须是显式事件,可重复、可审计、可回滚,不能改写历史事件;
- 工具副作用不能因为分支复制而重复执行。需要副作用的探索应使用 dry-run、幂等 key 或先执行后引用结果;
- 分支必须有预算、过期时间和最大数量,避免思考历史无限膨胀;
- callback 默认只召回主线和被显式选中的分支,不能让所有分支内容无条件挤入当前上下文。

这使 AAgent 的模型从“严格线性”扩展为“线性权威主线 + 可追踪候选分支 + 显式语义合并”:历史可以发散,事实和决策的权威写入仍然只有一条。

### 2.11 小模型 Draft-Review:以候选分支换取速度与丰富性

**状态:规划中,尚未实现**

可以进一步利用小模型做 draft,再由小模型或主 Agent 做 review,把它作为加速和提高思考内容丰富性的手段。关键不在于让小模型直接接管主 Agent,而在于让它生成低成本、可丢弃、可比较的候选材料。

一个可控的流程是:

```text
主线任务/未决问题
	↓
创建受预算约束的 draft 分支
	↓
小模型生成一个或多个候选草稿、假设、反例、问题清单
	↓
review 阶段检查事实依据、遗漏、矛盾、风险和可执行性
	↓
形成结构化 review 结果与建议修改
	↓
主 Agent 选择:采纳、部分采纳、继续探索或丢弃
	↓
通过 merge event 写入主线
```

Draft 和 review 可以由同一个小模型完成,也可以拆成不同提示词、不同小模型或不同温度的候选路径。为避免“自己写、自己证明”的虚假可靠性,review 至少应尽量改变视角,例如要求专门寻找反例、检查约束、核对证据和指出不确定性。高风险任务仍应由更强模型、人类或真实工具进行最终验证。

Draft-Review 的候选输出应区分:

- `draft`:尚未验证的方案、推理摘要或待确认事实;
- `review`:对 draft 的支持点、问题、反例、证据缺口和修改建议;
- `adoption`:主 Agent 对哪些内容采纳、拒绝或保留为未决问题的决定。

只有 `adoption` 产生的合并结果才有资格成为主线工作集中的结论。Draft 和 review 本身可以保存在分支历史中,作为后续召回、评估和模型改进的材料,但不能因为被小模型写出就自动升级为事实。

这种方式可能带来两类收益:

- **加速**:小模型先完成候选展开、格式整理、反例枚举和初步筛选,主 Agent 减少从空白开始的工作量;
- **丰富性**:多个低成本 draft 可以覆盖不同假设和表达路径,review 可以主动寻找盲点,提升主 Agent 接收到的候选空间质量。

代价也必须显式计入:小模型调用、review 调用、上下文整理和合并本身都会消耗 token 与延迟;低质量 draft 还可能增加主 Agent 的筛选负担。因此触发条件应根据任务复杂度、风险、预算和主 Agent 当前的不确定性决定,不能把 Draft-Review 变成所有请求的固定流水线。

它与 Skill-Tool、MCTS 和思考分支的关系如下:

- Skill-Tool 可以封装一个稳定的 draft 或 review 能力;
- MCTS 可以把多个候选路径组织成带评估的分支搜索;
- 思考分支提供统一的版本、来源、冲突和合并语义;
- 主 Agent 仍然是唯一的权威决策者。

## 2.12 方向之间的统一边界

上述能力都允许“候选结果先产生,权威结论后确认”,但不能因此模糊 AAgent 的核心边界:

> 可以有多条候选思考路径,但只能有一条经过显式合并、版本校验和统一历史记录的权威上下文主线。

异步工具、潜意识搜索、MCTS、思考分支和小模型 Draft-Review 都只能生成待评估的事件、候选 document 或分支变更。它们不能直接写入主线、宣称事实成立或执行不可逆的工具副作用。最终采纳必须经过主 Agent 的决策或明确的合并协议。

## 3. 已评估但废弃的方向

以下方向曾经具有一定吸引力,但当前判断没有足够实际价值,不再列入待实现路线图。保留它们是为了记录设计取舍,避免未来重复走回头路。

### 3.1 潜意识搜索

**状态:已废弃**

原设想是在 Document Callback 过程中,悄悄阻塞调用工具,或者发布一个异步任务,根据预先编制的规则或本地小模型的决策补充信息。它试图让 Agent 在显式思考之外,自动寻找可能遗漏的材料。

当前放弃这一方向,因为主动搜索已经能够满足信息补充需求。潜意识搜索会增加隐藏的工具调用、等待和调度复杂度,却没有带来相称的收益;它还会让一次 callback 到底做了什么变得更难观察和解释。

### 3.2 Router 机制

**状态:已废弃**

原设想是增加一个类似潜意识搜索的 router,通过小模型判断当前任务应该交给哪一种能力或路径,以此补充主 Agent 的决策。

当前判断是,这种额外的小模型路由层实际价值有限,会增加判断链和系统复杂度。Skill-Tool 已经足以承担专门能力的封装,没有必要再维护一套独立 router 机制。
