# Workflow 数据互通改动说明

## 这次改动是为了什么

这次改动的核心不是单纯增加几个导入、导出按钮，而是建立 **Workflow Editor 与 Agent 之间清晰、低成本的数据流通方式**。

此前，Editor 更像一个独立的 Workflow 制作工具，Agent 侧的 Workflow 管理与使用也相对独立。两者虽然处理的是同一种 Workflow，但缺少顺畅的交换入口：Editor 中完成的内容不容易交给 Agent 使用，Agent 中已有的 Workflow 也不方便快速送入 Editor 修改。

本次改动以完整的 Workflow JSON 作为双方共同的数据契约，并通过文件、文本、剪贴板和 URL 提供多种传递通道。这样，Workflow 可以在 Editor 与 Agent 之间双向流动，而不要求两个系统在界面、部署或代码层面紧密绑定。

更重要的是，**数据开始通过协议流通，本身就标志着 Editor 与 Agent 正在成为两个独立体**。如果二者只是同一个系统内部不可分割的模块，它们可以直接共享状态和内部实现；当二者改为通过约定的数据格式进行协作时，双方之间就出现了正式边界。协议负责连接边界两侧，而边界的存在确认了它们各自独立的身份。

因此，这次改动同时完成了两件事：建立 Editor 与 Agent 的连接，也宣告 Editor 与 Agent 的独立。

## 产品价值

### Editor 与 Agent 的数据互通更方便

用户现在可以完成一条完整的 Workflow 使用链路：

```text
Agent 中已有的 Workflow
  ↓ 导出
Editor 中打开并修改
  ↓ 导出
回到 Agent 中导入、管理和使用
```

数据既可以通过文件长期保存和传递，也可以通过文本或剪贴板快速搬运，还可以通过带 `workflow` 参数的 URL 直接打开 Editor。

这降低了在 Agent 和 Editor 之间切换时的操作成本。用户不再需要依赖数据库手工迁移、后台脚本或专用同步接口，便可以把 Workflow 从一个产品表面带到另一个产品表面。

### Editor 可以保持独立

Editor 不需要知道 Workflow 来自哪个 Agent 实例，也不需要直接访问 Agent 的数据库或内部接口。它只需要理解约定好的 Workflow JSON。

因此 Editor 可以：

- 独立部署和升级。
- 在没有 Agent 后端连接时编辑 Workflow。
- 被其他系统通过 URL、文件或文本调用。
- 不因 Agent 的存储方式变化而立即失效。

### Agent 不需要绑定某一个 Editor

Agent 负责 Workflow 的保存、管理和实际使用，但不必承担完整的可视化编辑能力，也不需要依赖当前 Editor 的内部实现。

只要遵守 Workflow 数据格式，Agent 可以接收当前 Editor、未来的新 Editor，甚至其他工具生成的 Workflow。Agent 与 Editor 的关系由“两个必须互相了解的模块”转变为“两个通过数据契约协作的产品能力”。

### 协议标志着独立

协议通常被理解为一种连接手段，但在这里它还有更重要的含义：**只有边界清晰的独立参与者，才需要通过协议相互理解。**

在建立 Workflow 交换协议之前，Editor 与 Agent 的关系是隐含的。二者处理相同数据，但彼此的职责、归属和连接方式没有被正式表达。导入导出能力出现后，这种关系变得明确：

- Editor 是 Workflow 的生产者和编辑者。
- Agent 是 Workflow 的管理者、消费者和运行者。
- Workflow JSON 是双方都承认的协议内容。
- 文件、文本、剪贴板和 URL 是承载协议的不同传输方式。

从这一刻起，Editor 与 Agent 不再需要依靠“处于同一系统内部”来维持合作。它们可以分别存在、分别演进，再通过协议重新建立联系。

所以协议具有双重作用：

1. **连接作用**：让 Workflow 可以稳定地在 Editor 与 Agent 之间流动。
2. **界定作用**：明确连接两端是两个拥有独立职责和生命周期的主体。

没有协议时，双方可能只是耦合在一起的内部组成；形成协议后，双方成为可以独立存在、又能够协作的两个系统。这里的独立不是互不相干，而是不再依赖对方的内部结构才能成立。

### 允许更高程度的解耦

导入导出能力形成了一层明确的产品边界。图中的箭头不只是数据通道，也是两个独立体之间的协议边界：

```text
┌──────────────────┐       Workflow JSON       ┌──────────────────┐
│ Workflow Editor  │  ←────────────────────→   │ Agent / WebUI    │
│ 负责创建与编辑    │  文件、文本、剪贴板、URL   │ 负责管理与使用    │
└──────────────────┘                            └──────────────────┘
```

双方共享的是协议，而不是页面状态、数据库连接或部署生命周期。由此带来的解耦包括：

- **界面解耦**：Editor 和 Agent 可以采用不同的页面结构与交互设计。
- **部署解耦**：两者可以独立运行，不要求位于同一个服务中。
- **存储解耦**：Editor 不需要理解 Agent 如何持久化 Workflow。
- **版本演进解耦**：只要数据契约保持兼容，双方可以分别迭代。
- **工具生态解耦**：未来其他工具也可以生产或消费相同的 Workflow JSON。

这种解耦不是切断联系，而是将联系收敛到明确、可验证的数据边界上。协议越明确，双方越不需要了解彼此内部；双方越能脱离彼此独立运行，这条协议边界也就越真实。

## 用户工作流的变化

### 从 Agent 到 Editor

用户可以从 Agent 的 Workflow 管理页将 Workflow 导出到剪贴板或文件，再交给 Editor 打开和修改。Editor 的文本导入提供“覆盖”和“在新页面打开”两个明确动作，因此用户可以选择替换当前工作，或在保留当前画布的情况下查看另一个 Workflow。

### 从 Editor 到 Agent

用户在 Editor 中完成 Workflow 后，可以导出到剪贴板或文件，再从 Agent 的 Workflow 管理页导入。Agent 侧导入后仍进入原有管理和确认流程，因此外部 Workflow 不会绕过 Agent 自身的管理边界。

### 通过 URL 进入 Editor

Editor 支持从 `workflow` URL 参数读取完整 Workflow。这不仅减少了一次手工粘贴，也为后续增加“一键在 Editor 中编辑”、Workflow 分享链接和其他系统拉起 Editor 留出了简单入口，无需先建设复杂的双向 API 或共享页面状态。

## 为什么保留多种传递方式

| 方式 | 适用场景 | 产品意义 |
| --- | --- | --- |
| 文件 | 归档、备份、跨设备传递 | 稳定、可保存、与浏览器权限无关 |
| 文本 | 调试、审查、人工修改、聊天传递 | 内容可见、可编辑、失败时容易修正 |
| 剪贴板 | 同一设备上的快速搬运 | 操作步骤少，适合 Editor 与 Agent 间即时流转 |
| URL | 页面跳转、系统间拉起 Editor | 易于集成，可作为轻量调用入口 |

这些方式不是简单重复，而是避免 Editor 与 Agent 只能依赖某一种同步机制。即使剪贴板权限不可用，用户仍可使用文本或文件完成相同目标。

## 本次形成的产品原则

### Workflow 是可携带的数据

Workflow 不应被锁在某一个页面或数据库里。用户应当能够看见、导出、传递、重新导入，并在不同工具中继续使用它。

### 协议连接独立体

Editor 与 Agent 之间只共享完成协作所必需的 Workflow 协议，不共享内部状态和实现。协议不是将两个模块重新绑在一起，而是让两个已经拥有独立边界的产品能力可以稳定合作。

### Editor 负责编辑，Agent 负责运行与管理

Editor 专注于创建、查看和修改体验；Agent 专注于 Workflow 的持久化、组织、调用和运行。导入导出负责连接两者，但不要求任何一方侵入另一方的职责。

### 数据交换必须显式且可控

导入操作需要先校验，再修改当前状态。可能覆盖当前编辑内容时，应给用户明确选择；选择在新页面打开时，不应改变当前画布。

### 互通能力应当可以扩展

只要继续维护 Workflow JSON 数据契约，未来可以在当前基础上增加一键进入 Editor、编辑后提交回 Agent、Workflow 分享链接、模板市场和第三方工具接入，而无需先将 Editor 与 Agent 合并成同一个系统。

## 需求与实现附录

### 能力落点

- Agent 的 Workflow 管理页支持从文件和文本导入。
- Agent 的 Workflow 管理页支持导出文件和导出到剪贴板。
- Editor 支持从文件和文本导入。
- Editor 支持导出文件和导出到剪贴板。
- Editor 支持通过 `workflow` URL 参数载入 Workflow。
- Editor 的文本导入支持覆盖当前页面或在新页面打开。
- 有效的剪贴板内容可以自动预填到文本导入窗口。
- 两个页面的操作文案、分组、颜色和图标语义得到统一。

### 关键约束

- 所有通道传递完整的 Workflow JSON，避免不同入口产生不同数据语义。
- 导入内容先校验再写入，防止无效数据破坏当前编辑状态。
- 在新页面打开时不修改当前画布。
- Agent 的导入仍经过自身确认流程，不绕过管理边界。
- 剪贴板不可用时仍可通过文本和文件完成交换。

### 验证范围

- 本次涉及的 HTML、JavaScript 和 CSS 文件已通过 VS Code 静态诊断。
- 尚未进行完整的浏览器自动化交互测试。
- 剪贴板权限、弹窗拦截和不同屏幕宽度下的效果仍需在实际浏览器中确认。

## 结论

短期看，这次改动减少了用户在 Agent 和 Editor 之间搬运 Workflow 的步骤，并补齐了导入、导出和防误覆盖体验。

长期看，它让 Editor 与 Agent 可以围绕共同的数据契约独立演进。Editor 不必绑定 Agent 的存储与运行实现，Agent 也不必绑定某一个编辑器。数据互通因此更方便，系统允许的解耦程度也更高，并为后续的一键编辑、分享和第三方工具接入留下了清晰路径。

这次改动的标志性意义在于：**Workflow 的流通形成了协议，协议形成了边界，边界确认了 Editor 与 Agent 是两个需要通过协议连接的独立体。** 二者今后的关系不再建立在内部耦合之上，而是建立在明确契约之上。协议让它们保持连接，也让它们真正独立。
