# 07 WebUI 优化记录

> 本文记录 WebUI 从"三面板监控"重写为"统一任务流控制台"过程中的关键优化与背后的思考。只回答一个问题:**这些改动为什么这样做?**

## 1. 重写背景与目标

旧 WebUI 是三个并列面板:Redis 队列 / Worker 状态 / MongoDB 历史,由前端并行发起三次 API 调用各自渲染。问题在于:

- 数据分散在三个面板里,看不出一个事件从"排队 → 执行 → 落库"的完整流转;
- 三个接口的时序无法对齐,状态割裂;
- 业务上有一个简单事实:**一个事件不是在 Redis 里,就是在 MongoDB 里**。

因此重写目标定为:前端呈现一个**统合的列表**——已完成的任务、正在进行的任务、将要进行的任务,全部出现在一条时间流里,并按状态着色、按条件筛选。

## 2. 架构级优化:统一聚合接口

### 2.1 一次请求,三个数据源

新增 `GET /api/events`,由后端一次性完成合并:

1. 读 Worker 状态(`aagent:worker:status`):正在处理则把该事件作为 running 项放在列表最前;
2. 读 Redis 队列(`agent_tasks`):`LLen` 得到真实的 pending 总数,`LRange` 从队尾(消费侧)读取并反转,`Position=1` 即下一个将被 `BRPOP` 的事件;
3. 读 MongoDB `event_history`(按 `created_at` 倒序):作为已处理历史;
4. 汇总 `Summary{pending, running, done}`,并返回各数据源的 `Warnings`(某个源失败不影响其他源展示)。

### 2.2 指纹去重

运行中的事件在 `handle_task()` 开始时已写入 MongoDB,所以它同时出现在"Worker 状态"和"历史"两个源里。用事件内容的 FNV-1a 指纹计算 `eventFingerprint`,MongoDB 结果中**只跳过第一条匹配该指纹的文档**,其余正常展示——running 事件不会重复出现。

### 2.3 收益

- 前端只关心一个接口,一轮轮询即可获得全部状态,一致性由后端保证;
- 数据源故障降级为告警条,而不是整页空白;
- 旧的 `/api/queue`、`/api/status`、`/api/history` 三个接口被删除,前端逻辑大幅简化。

## 3. 前端模块化(不引框架)

拆成五个文件,零构建链:

| 文件 | 职责 |
|------|------|
| `index.html` | 页面结构(顶栏、统计卡片、筛选、事件列表) |
| `styles.css` | 全部样式(网格布局、状态色、响应式断点) |
| `app.js` | 状态与编排:轮询、筛选、Worker 状态渲染、暂停/恢复 |
| `api.js` | 唯一的网络层:`fetchEvents(limit)` |
| `render.js` | 纯渲染:事件行创建/更新、类型下拉、预览文本 |

**为什么不用 Vue/React**:这个控制台的规模就是"一个列表 + 若干筛选",原生 ES Modules 足够,还省掉构建链、`node_modules` 和 Docker 镜像体积。拆模块的目的不是"用框架",而是**让数据、渲染、编排各自独立可测**。

## 4. 渲染性能优化(本次核心)

### 4.1 闪烁问题的根因

现象:每轮轮询(默认 1s),整个事件列表"闪"一下。排查时先怀疑了轮询本身,但真正根因是一条链条:

1. CSS 给每一行定义了入场动画 `animation:reveal 220ms ease both`(透明 + 下移 4px 淡入);
2. `renderEvents` 每轮都执行 `container.replaceChildren(fragment)`;
3. 即使行是复用的同一个 DOM 节点,**从 DOM 中移除再重新插入,会强制重播该节点的 CSS 动画**;
4. 每轮 150 行集体重播入场动画 → 视觉上的"一闪一闪"。

关键认知:**问题不在数据,而在"DOM 复用"与"CSS 动画重播"的交互**。数据其实每轮都差不多,真正在动的是动画。

### 4.2 修复一:动画只属于新建行

```css
.event-row { ... }                    /* 原:animation:reveal 220ms 在这里 */
.event-row.enter { animation:reveal 220ms ease both; }   /* 现:只给新建行 */
```

新建行时加 `.enter` 类,监听一次 `animationend` 后移除:

```js
row.classList.add('enter');
row.addEventListener('animationend', () => row.classList.remove('enter'), { once: true });
```

复用行不持有 `.enter`,被 `replaceChildren` 插回时也不会有动画,闪烁消失。

### 4.3 修复二:内容签名跳过重渲染

即使修了动画,每轮仍会做无谓的 DOM 更新。加一个"脏检查":

```js
const signature = items.map((i) =>
  `${i.id}|${i.status}|${i.position ?? ''}|${eventPreview(i)}|${eventTime(i)}`
).join('\u0001');
if (signature === state.listSignature) return;  // 数据没变,不碰 DOM
```

**数据没变就不该碰 DOM**。这既消除了动画重播,又省掉每轮 150 行的文本写入与重排,CPU 占用也降下来了。

### 4.4 增量 DOM 复用

渲染时用 `dataset.id` 建 Map:已存在的行只更新内容,不存在的行才新建。避免整表重建,也为 4.2/4.3 打下基础。

## 5. Docker 构建提速

### 5.1 根因

旧 Dockerfile 把 `go mod tidy` 放在 `COPY . .` 之后:

```dockerfile
COPY . .
RUN go mod tidy && go build ...
```

`go mod tidy` 每次构建都要**重新解析整个模块图并联网核对版本**——这就是"每次 build 都要 download"的元凶。只要任意源码或前端文件变化,这一层失效,连带重新下载。

### 5.2 修复(保守方案)

```dockerfile
COPY go.mod go.sum ./
RUN go mod download        # 这层只依赖依赖清单,几乎不变,层缓存长期命中
COPY . .
RUN go build ...           # 源码再变也不会触发重新下载
```

两点说明:

- 删掉 `go mod tidy`:`go.sum` 本来就齐全且与源码一致,`tidy` 是纯开销;
- 为什么选"层缓存"而不是 BuildKit 缓存挂载(`--mount=type=cache`):两者都有效,但层缓存**零构建器依赖、任何 Docker 版本都可靠**。代价仅是 `go.mod` 变更时会全量重下——本项目的依赖几乎不动,这个代价可以接受。保守、简单、可预期。

## 6. 图标修复:CSS 拼图 → SVG

原刷新按钮的箭头是用 CSS 拼出来的(`border` 圆环 + `::after` 三角形 + `rotate(-38deg)`),方向歪、像素级难调。换成内联 SVG(feather 风格 `refresh-cw`):

```html
<svg class="refresh-icon" viewBox="0 0 24 24" stroke="currentColor" ...>
  <polyline points="23 4 23 10 17 10"/>
  <path d="M20.49 15a9 9 0 1 1-2.12-9.36L23 10"/>
</svg>
```

原则:**图形类 UI 元素优先用 SVG,不要用 CSS 手拼**。SVG 方向天然正确、可缩放,`stroke="currentColor"` 自动继承按钮的悬浮/禁用变色,且内联 SVG 不受 CSP `img-src` 限制。

## 7. 可复用的优化原则

1. **先找根因,再谈修复**。闪烁的根因不是轮询频率,而是 DOM 插回触发动画重播;构建慢的根因不是网络,而是 `go mod tidy`。
2. **动画与 DOM 复用天然冲突**,是"刷新闪烁"类 bug 的高发来源。让动画只属于"新建"状态。
3. **数据没变就不该碰 DOM**。加一个廉价签名做脏检查,收益远超那点字符串拼接成本。
4. **构建慢先查"每次都在做什么"**,而不是盲目堆缓存。
5. **能用标准组件(SVG)就不用手绘(CSS)**,能用一个接口解决的事就不要三个接口。
6. **先保守后激进**:BuildKit 缓存挂载虽好,但层缓存方案零风险、可预期,足够解决问题时就选它。
