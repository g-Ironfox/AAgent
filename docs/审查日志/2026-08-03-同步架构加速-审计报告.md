# 2026-08-03 同步架构加速（docs/09）审计报告

> 性质：历史快照，记录对 [09-同步架构加速](../09-同步架构加速.md) 的一次文档审计过程与结论。修订前的原稿已逐字保存为 [2026-08-03 同步架构加速 原稿快照](2026-08-03-同步架构加速-原稿快照.md)（SHA-256 与原稿一致）。

## 1. 审计起因

用户反馈：docs/09 “感觉有点中二”。审计目标是判断这是单纯措辞问题，还是文档存在更深层的结构问题，并给出修订方向。

## 2. 审计过程

1. **通读 09 全文，并与 [00-设计哲学](../00-设计哲学.md)、[01-系统架构](../01-系统架构.md)、[05-路线图与创新](../05-路线图与创新.md) 交叉对照。**
2. **初步误判**：审计中曾认为 09 §3.4“在当前权威思考期间为未来预行”与 00 中“同一时刻最多存在一个 LLM 调用”直接冲突，倾向于判定 09 提出了与现有架构不兼容的扩展。
3. **关键澄清（用户提出）**：判断一个能力是否破坏原框架，标准不是“是否出现并发”，而是**可插拔性**——添加它和去除它都不会带来根本性的变化。Draft-Review（05 §2.11）、Git 式思考分支（05 §2.10）正是按此标准设计的：它们是候选计算层，移除后系统退化为原样，因此不构成对原架构的破坏。
4. **据此修正判断**：09 描述的并发候选计算与单一权威主线兼容。真正需要修订的不是架构内容，而是表述方式与术语密度。

## 3. 最终结论

### 3.1 兼容性判据：可插拔性（本次审计的重要产出）

设基础系统的权威状态转移为：

$$
S_{n+1} = F(S_n, E_n)
$$

加入并发候选计算后：

$$
D_n = G(S_k, E, \text{budget}), \quad k \le n
$$

$$
S_{n+1} = F(S_n, E_n, \operatorname{validate}(D_n, S_n))
$$

其中 $D_n$ 只是候选。只要满足下列条件，候选计算层就是对原架构的**保守扩展**，而不是另一套架构：

- 候选计算只读取快照，不直接推进权威上下文；
- 候选结果可丢弃，缺失或失败不阻断主线；
- 采纳时基于**当前版本**重新校验，不能凭创建候选时的旧版本直接提交；
- 所有事实、决策和副作用仍由单 worker 串行提交；
- 候选分支不绕过统一历史和合并协议；
- 关闭候选计算层后系统语义不变，变化的只是延迟、成本或结果丰富度。

推论：00 中“同一时刻最多存在一个 LLM 调用”的表述过宽，把**权威 LLM 调用**与**只读候选 LLM 调用**混为一谈。该表述在语义上应限缩为“同一时刻最多存在一个推进权威上下文的 LLM 调用”。本次只修订 09；00 的措辞限缩留作后续待办（见 §6）。

### 3.2 09 的真正问题：叙事包装超过设计密度

问题不是使用了“权威”这个词——“权威历史”“权威上下文”在 00/01 中是既有合理用法。问题在于 09 把一个常见的工程模式：

> 推测执行生成候选结果，主流程基于最新版本校验后决定是否提交。

包装成了“权威思考、现实影响、获得权威性”的完整叙事。术语密度高于实际设计密度，具体表现：

| 位置 | 问题 | 性质 |
|------|------|------|
| §3.1 “纲领：权威的意义在于……” | 宣言式语句，不含任何可执行的设计信息 | 文风 |
| §3.1 自造术语 ADP（权威决策点） | 业界已有对应概念：提交点 / 校验后提交（validate-then-commit） | 术语 |
| §3.1 “副作用的产生不是非权威思考的责任，而是权限管理未能守住权威边界的结果” | 归责修辞，实际内容只是“候选计算不得拥有副作用工具权限”一句话 | 文风 |
| §3.1/§3.4 “获得权威性”“权威只能在 ADP 上产生” | 把“通过版本校验后被采纳”这一普通操作上升为叙事概念 | 术语 |
| §3.2/§3.3 “非权威并行思考”“预行” | 即“并发候选计算”与“空闲预计算”，自造词增加理解成本 | 术语 |
| 全文 | 没有任何关于快照版本、失效判定、预算、命中率、降级路径的具体设计 | 设计密度 |

### 3.3 权限管理议题保留，但换正常的名字

用户确认：候选计算的权限管理是真实且重要的议题，应当保留。修订方向是把相关概念映射为常规工程术语：

| 原稿表述 | 修订后表述 |
|----------|-----------|
| 权威决策点（ADP） | 主线提交点（主 worker 的决策与提交时刻） |
| 权威思考 / 正式思考 | 主线推理 |
| 非权威思考 / 候选思考 | 候选计算（推测执行） |
| 预行 | 空闲预计算 |
| 获得权威性 / 被 ADP 采纳 | 通过版本校验后被采纳 |
| 权威边界 / 权限管理 | 候选计算的工具权限边界与副作用隔离 |
| 副作用（权限管理失败的影响） | 副作用泄漏 |

### 3.4 修订原则

1. 删除宣言式语句与归责修辞，只保留可执行的设计陈述；
2. 自造术语全部替换为常规工程术语，首次出现时可用一句话定义；
3. 保留并显式化权限管理议题：候选计算的工具权限边界、副作用隔离、泄漏的判定；
4. 补充原稿缺失的设计密度：快照版本、候选失效条件、预算、观测指标、降级路径；
5. 与 05 §2.10/§2.11/§2.13 的既有术语（候选分支、merge event、采纳）对齐，不再另起一套词汇。

## 4. 修订执行

按 §3.3/§3.4 重写 [09-同步架构加速](../09-同步架构加速.md) 全文。原稿一字未删地保留在快照文件中；本报告与快照共同构成修订前后的对照证据。

## 5. 经验

- **“中二感”的可操作定义**：术语密度 ÷ 设计密度过高。判断时数一下文档自造了多少名词、又给出了多少可执行的约束（版本、预算、失效条件、降级路径），比值失衡即为信号。
- **先保存证据再修订**：原稿快照 + 哈希校验先行，审计报告记录判断的修正过程（包括审计者自己的误判），避免“修订后无处对照”。
- **架构兼容性用可插拔性判断**，而不是用“有没有并发”判断；并发候选计算与串行权威提交可以共存。
