> 审查日期:2026-08-02。审查范围:`webui_py/main.py`(FastAPI,端口 8081),以及为核对契约而交叉阅读的 `agent/task_worker.py`、`agent/history_repository.py`、`docs/webUI/前端API格式.md`。

## 1. 本轮已完成的改动

目标:在**不改变任何对外 API 契约**的前提下,消除易引发 500 的类型假设,并把聚合逻辑拆成单一职责函数。已通过编辑器静态错误检查,未在 Docker 环境实测(本机无运行环境)。

### 1.1 已修复的健壮性问题

| 位置 | 问题 | 修复 |
|------|------|------|
| `read_worker_status()` | 合法 JSON 但顶层非对象(如 `null`/数组/字符串)时,`status.get(...)` 抛 `AttributeError` → `/api/events` 500 | 增加 `isinstance(status, dict)` 校验,非对象返回 `invalid` |
| `read_worker_status()` | `processing` 状态只检查 `"event" in status`,若 `event` 为 `null` 会被放行,与 `summary.running` 语义冲突 | 收紧为 `event` 必须是 dict,否则 `invalid` |
| `terminal_history()` | `document.pop("_id"/"created_at")` 原地修改 MongoDB 返回的文档 | 改为 `.get()` + 过滤重建 `event` 字典,消除副作用 |

### 1.2 重构:事件聚合拆分

原 `event_snapshot()` 一个函数内同时完成 Worker 状态读取、Redis 队列读取、MongoDB 历史读取与合并。拆分为三个阶段函数:

- `worker_stage()` — 读取 Worker 状态,构造 running item 与指纹;
- `pending_stage(limit)` — 读取 Redis 队列,构造 pending items 与计数;
- `history_stage(limit, running_fingerprint)` — 读取 MongoDB 历史,剔除 running 去重项,构造 done items;
- `event_snapshot(limit)` — 只负责按顺序合并三路结果,生成统一快照。

输出结构保持逐字段一致:历史(正序)→ running → pending(消费顺序),`summary` 三计数、`sources`、`warnings` 语义均未变。

### 1.3 其它清理

- `validate_limit()` 返回 `int | JSONResponse`(混用成功值与错误对象)→ `limit_error()` 返回 `JSONResponse | None`,路由调用处更直白;
- pending 计数变量 `seen` 更名 `counts`;
- `worker_source_status(state)` 参数类型从 `str` 放宽为 `Any`,配合非 dict 校验后的容错。

## 2. 与数据源的契约核对(均已验证一致)

| 数据源 | 实际写入形态 | webui 侧假设 | 结论 |
|--------|--------------|--------------|------|
| Worker 状态 (`task_worker.py`) | `{"state": "idle", "updated_at": ISO}` / `{"state": "processing", "event": <完整事件 dict>, "started_at": ISO}` | 校验 state 合法集合;processing 必须带 dict event | ✅ 一致 |
| MongoDB 历史 (`history_repository.py`) | `{**事件, "created_at": datetime}` | 指纹前剔除 `created_at`;`_id` 由投影 `{"_id": 0}` 排除 | ✅ 一致 |
| 指纹序列化 | 事件字段均为 JSON 兼容类型 | `json.dumps(..., sort_keys=True)` 不会遇不可序列化类型 | ✅ 安全 |
| 事件顺序/计数 | — | 历史正序 → running → pending;`summary.history` = 窗口内 done 数 | ✅ 与重构前一致 |

## 3. 发现的问题(按优先级)

### 3.1 P1 建议修复

**P1-1:FastAPI 422 校验错误破坏"统一错误格式"契约**
- 位置:`TerminalRequest`(`extra="forbid"`)+ Pydantic 类型校验。
- 现象:请求带多余字段、`files` 传 `null`、`message` 非字符串时,返回 **422**,body 为 `{"detail": [...]}`;而 `docs/webUI/前端API格式.md` 约定所有错误统一为 `{"error": "<中文提示>"}`。前端 `api.js` 只读 `body.error`,此类错误会拿到空提示。
- 建议:注册 `RequestValidationError` 异常处理器,统一转 `400 {"error": "请求参数不合法"}`;同步修订前端 API 文档。

### 3.2 P2 维护性改进

- **P2-1 配置导入期崩溃风险**:`REDIS_DB = int(env(...))`、`MONGO_PORT = int(env(...))` 在模块导入时执行,环境变量非数字会直接导致 ASGI 应用启动失败,且堆栈看不出是哪个变量。建议抽 `Settings`(dataclass 即可),集中解析并给默认值。
- **P2-2 时间格式不一致**:`submit_terminal` 的 `time` 用 `...Z` 后缀;`fetched_at` 由 FastAPI 序列化为 `...+00:00`。建议加 `utc_now_iso()` 助手统一。
- **P2-3 命名遗留**:`MAX_TERMINAL_RUNES` 的 `RUNES` 是 Go(rune)遗留,建议改名 `MAX_TERMINAL_CHARS`。
- **P2-4 元组返回值**:`worker_stage()` 返回 5 元组,位置参数易错,可改 `@dataclass` 表达阶段结果。

### 3.3 明确不改的点

- `limit_error()` 返回 `JSONResponse | None` 虽非最"FastAPI 风格",但 `HTTPException` 会返回 `{"detail": ...}` 破坏契约,当前写法是有意为之,保留。
- `pending_stage` 中 `llen`/`lrange` 之间的小竞态是原有设计,`lrange` 越界安全,不改。
- 同步 `def` 路由 + 阻塞 I/O:FastAPI 自动放入线程池执行,不卡事件循环,无需改 async。
