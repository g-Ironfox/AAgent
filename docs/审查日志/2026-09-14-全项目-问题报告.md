## 0. 结论

系统骨架自洽:Workflow 的解析器 / 校验器 / 契约表 / 执行器四者在端口与连接语义上互相吻合;管理页保存链的字段结构与 `WorkflowRequest(extra="forbid")` 严格对应;WebUI 的输入防御面(请求体上限、Lua 原子替换、指纹校验、错误契约)完整。

## 1. 致命问题(Fatal)

### F-01 LLM 节点的 `model` 参数在运行时被完全忽略

**证据链**

1. 编辑器为 LLM 节点生成 `arguments.model`(模型配置的 `_id`):`workflow_editor/static/workflow/domain/node-contract.js::createNode` 中 `if (type === 'llm') return { ..., model: '', ... }`;检查器负责填充该字段。
2. 管理页保存时校验该模型必须存在且启用:`webui_py/workflows.py::update_workflow` 中
   `model_ids = [ObjectId(node_arguments(node).get("model", "")) for node in llm_nodes]`,再以
   `{"_id": {"$in": model_ids}, "enabled": True}` 查 `model_configs`,缺失即返回 400。
3. 运行时**从不读取** `model`:`agent/workflow_nodes.py::workflow_llm` 全文没有任何 `node_argument(node, "model")`;它直接调用
   `content, reasoning, tool_calls = chat_with_deepseek(messages, tools=tools)`。
4. `agent/llm.py` 的模型来源是进程级常量:
   `DEEPSEEK_BASE_URL = os.environ["DEEPSEEK_BASE_URL"]`、`DEEPSEEK_API_KEY = os.environ[...]`、`DEEPSEEK_MODEL = os.getenv("DEEPSEEK_MODEL", "deepseek-v4-pro")`。
5. 全 `agent/` 目录检索 `MONGO_MODEL_COLLECTION` / `model_configs` / `base_url` / `api_key`:命中项全部在 `llm.py`(env 常量)与 `tools/*`(各工具自己的 env 常量)中,**没有任何一处读取 MongoDB 的模型集合**。

**后果**

- 用户在编辑器里切换模型、在管理页保存成功、运行时行为完全不变。
- 模型集合的 `provider`、`model`、`base_url`、`api_key`、`enabled` 五个字段对运行时零影响;`enabled` 只在保存时起拦截作用。
- 无法使用任何非 `DEEPSEEK_*` 环境变量的供应商。

**建议**

`workflow_llm` 按 `model` 读取模型配置(进程内缓存 + 短 TTL),调用 `llm.openai_llm_api(messages, model["model"], model["base_url"], model["api_key"], tools)`。若有意只支持单模型,则应在编辑器禁用该字段并在管理页停止校验,避免"看起来能配、实际不生效"。

### F-02 节点执行异常静默中断,不产生任何失败反馈

**证据链**

1. `agent/task_worker.py::main()` 的结构是:内层 `try/finally` 只负责恢复 worker 状态;
   ```python
   try:
       set_worker_status({"state": "idle", ...})
       task = pop_from_queue(MAIN_AGENT_QUEUE_NAME, timeout=5)
       ...
       try:
           handle_task(task)
       finally:
           set_worker_status({"state": "idle", ...})
   except Exception as e:
       print("agent处理失败:", e)
       traceback.print_exc()
       time.sleep(2)
   ```
   异常只被打印和延时。
2. `handle_task()` 中 `record_history(e)` 在执行**之前**调用,因此原始事件确实入库;但执行期异常不会产生任何新的 `response` / 失败事件。
3. `workflow()` 处理器内部没有任何 `try/except`;`run_workflow_map()` 也没有。因此下列任一情况都会直接冒泡:
   - `validate_workflow(workflow_document)` 抛 `WorkflowValidationError`;
   - `workflow_foreach` 的 `raise ValueError(f"foreach input must be a list: node {node.get('id')}")`;
   - `workflow_router` 的 `next_successor(node, f"branch-{key}")` 抛 `ValueError`;
   - `workflow_tool_call` 的 `raise ValueError("tool_call input is missing: ...")`;
   - `workflow_llm` 中 `chat_with_deepseek` 的 HTTP 异常(见 F-04);
   - `workflow_workflow` 的 `raise ValueError("recursive workflow call detected: ...")`。

**后果**

用户在终端提交指令后,队列中的事件被消费并落库,但终端与事件流页面**看不到任何新内容**;异常只存在于容器 stdout。也没有出错节点 id,无法定位。

**建议**

在 `workflow()` 入口包一层 `try/except`,把 `workflow_name`、当前节点 id、异常类型与摘要作为 `response`/`error` 事件 `publish_to_queue`,使终端与历史可观察;节点级可在 `run_workflow_map` 的循环内附加 `node_index` 信息。

### F-03 子 Agent 回发链路不闭环,群消息永远发不出去

**证据链**

1. `qqbot_consumer/queue_consumer.py::send_group_message` 构造并发布:
   ```python
   e = {
       "event_type": "rpc_apply",
       "payload": {
           "subagent_name": "qqbot",
           "callback_queue_name": QQ_AGENT_QUEUE_NAME,
           "tool_name": "qq_send_group_msg",
           "tool_arguments": {"group_id": group_id, "message": message},
       },
   }
   publish_to_queue(MAIN_AGENT_QUEUE_NAME, e)
   return "请求中"
   ```
2. `agent/task_worker.py::rpc_apply` 读取 `payload` 后重新发布,但把字段放在了**事件顶层**而非 `payload`:
   ```python
   e = {
       "event_type": "rpc_review",
       "subagent_name": subagent_name,
       "callback_queue_name": callback_queue_name,
       "tool_name": tool_name,
       "tool_arguments": tool_arguments,
   }
   publish_to_queue(MAIN_AGENT_QUEUE_NAME, e)
   ```
3. `rpc_review` 的处理器是空实现:`def rpc_review(e): pass`。
4. 调用方在群内被 @ 时走这条路:`handle_event` → `chat_with_deepseek` → `send_group_message(...)`,随后打印 "请求中" 即返回。

**后果**

QQ 群内 @ 机器人时,LLM 生成的内容**没有任何发送路径**。私聊路径(`publish_to_queue(MAIN_AGENT_QUEUE_NAME, event)`)是通的,行为不一致。

**建议**

二选一:(a) 实现 `rpc_review`(调用审批 + 通过 `callback_queue_name` 把工具结果回发),并把重发布事件的字段统一放进 `payload`;(b) 删除 `rpc_apply`/`rpc_review` 链路,让 `qqbot_consumer` 直接调用发送接口。

### F-04 LLM 无文本输出时,`output → tool_call` 主链路必然失败

**证据链**

1. `agent/workflow_nodes.py::workflow_llm` 无条件传播 content:
   ```python
   content, reasoning, tool_calls = chat_with_deepseek(messages, tools=tools)
   propagate_workflow_output(workflow_map, node, "output", content)
   ```
2. `agent/llm.py::openai_llm_api` 返回 `res['content']`。当模型只返回 tool_calls 时,OpenAI 兼容响应的 `content` 为 JSON `null`,即 Python `None`。
3. `propagate_workflow_output` 把 `None` 写入目标槽位 `target_slot[2] = value`。
4. `read_workflow_input` 用 **`is not None`** 判定"有无值":
   ```python
   return input_slot[2] is not None, input_slot[2]
   ```
5. 因此 `workflow_tool_call` 读到 `has_tool_call == False`,抛出
   `ValueError(f"tool_call input is missing: node {node.get('id')}")`。

**后果**

"LLM 节点 → Tool Call 节点"是本系统最核心的一条编排模式(LLM 产出 `tool_calls`,由 Tool Call 节点执行)。只要模型这一次没有同时产出文本,该链路即失败,并进一步落入 F-02 变成静默无响应。

**建议**

区分"槽位无来源"与"来源值为 None"。最小改动:`workflow_llm` 中把 `None` 归一化为 `""`(或对 `output` 端口在 `None` 时跳过传播);更彻底的做法是让 `data_inputs` 槽位用一个显式的 `connected` 标记,而不是靠值是否为 `None` 判断。

## 2. 高危问题(High)

### H-01 QQ 子 Agent 队列是后进先出(LIFO)

**证据链**

- 生产端 `qqbot/queue_client.py::publish_to_queue`: `client.lpush(queue_name, ...)` — 从**头部**入队。
- 消费端 `qqbot_consumer/queue_client.py::pop_from_queue`: `client.blpop(queue_name, timeout=timeout)` — 从**头部**出队。
- `qqbot/listener.py::listen()` 用 `asyncio.to_thread(publish_to_queue, QQ_AGENT_QUEUE_NAME, task)` 投递。
- `qqbot_consumer/queue_consumer.py::main()` 用 `pop_from_queue(QQ_AGENT_QUEUE_NAME, timeout=5)` 消费。
- **对比**:主队列 `agent/queue_client.py::publish_to_queue` 是 `lpush`,`pop_from_queue` 是 **`brpop`** → 主队列是 FIFO。

**后果**

同一个仓库内两条队列语义相反。QQ 子 Agent 队列在积压时按**到达顺序的逆序**处理:先来的消息最后处理。若消息之间存在依赖(例如"先发的上下文、后发的追问"),子 Agent 会用倒置的上下文作答。

**建议**

把 `qqbot_consumer/queue_client.py::pop_from_queue` 改为 `brpop`(与主队列一致),或把 `publish_to_queue` 改为 `rpush` 并保持 `blpop`。二者取其一,并保证跨服务的生产/消费方向成对。

### H-02 全部 HTTP 接口无任何鉴权,且端口对外发布

**证据链**

- `webui_py/main.py` 仅注册三个中间件:`security_headers`、`request_logger`、`request_body_guard`;全文无认证依赖、无 CORS 配置、无限流。
- 各路由工厂(`events.py`、`workflows.py`、`models.py`、`documents.py`、`subagents.py`、`settings.py`)均未声明 `Depends(...)` 鉴权。
- `docker-compose.yml` 中 `webui_py` 发布 `"8081:8081"`,`workflow_editor` 发布 `"8082:8082"`。
- `workflow_editor/main.py` 同样只有安全头与日志中间件,无鉴权。

**后果**

同一网段(或任何能访问宿主端口)的任意客户端可以:

| 能力 | 接口 |
| --- | --- |
| 读取全部供应商 API Key 明文 | `GET /api/models` |
| 读取/改写/删除全部文档 | `/api/documents*` |
| 删除、篡改队列中的待执行事件与历史记录 | `DELETE/PUT /api/events` |
| 向 Agent 直接下达指令 | `POST /api/terminal` |
| 改写/删除 Workflow、切换当前激活 Workflow | `/api/workflows*`、`PUT /api/settings` |
| 改写子 Agent 的文档选择 | `PUT /api/subagents/{id}/settings` |

**建议**

部署层面至少:把 8081/8082 绑定到 `127.0.0.1` 或置于带鉴权的反向代理后;代码层面增加一个共享的 Token 校验依赖。同时在 `main.py` 里对写操作接口加限流。

### H-03 `GET /api/models` 明文返回 `api_key`

**证据链**

`webui_py/models.py::model_response` 直接回填密钥:

```python
def model_response(document: dict[str, Any]) -> dict[str, Any]:
    return {
        ...
        "api_key": document.get("api_key", ""),
        ...
    }
```

`list_models()` 返回 `{"items": [model_response(item) for item in items]}`,即**列表接口**就把所有密钥明文吐给前端;模型编辑页原样回填显示。

**对照**:`workflow_editor/main.py::list_models` 的投影是 `{"name": 1, "model": 1, "provider": 1}`,返回体只含 `id/name/model/provider/enabled`,**不泄露密钥**。同一份数据在两个服务上策略相反。

**后果**

与 H-02 叠加后,任意同网段客户端一次 GET 即可拿到全部供应商密钥。

**建议**

列表与详情改为返回 `has_api_key: bool`;更新时若 `api_key` 为空字符串则保持原值不变。若确需回显,则应把该接口限制在已鉴权的管理通道内。

### H-04 保存面校验弱于执行面,可保存执行期必然失败的图

**证据链**

- 执行侧 `agent/workflow_validator.py::validate_workflow` 强制下列规则:
  - 恰好一个 `input` 节点、至少一个 `output` 节点;
  - `router.arguments.branches` 非空、id/name 各自唯一;
  - `construct_content` 的 `append_items` 非空且 `dataInputPorts` 必须与 port 型 item 完全一致;
  - `construct_list` 的 `initial_value_count ∈ [0,20]` 且 `dataInputPorts` 必须等于 `{item_type}-in-{i}`;
  - `foreach.item_type ∈ {content, message}`;
  - `tool.parameters` 为非空字符串、无重复;
  - **所有控制端口必须被连接**(`control ports must be connected`),且控制输出只能有一个后继、数据输入只能有一个来源。
- 保存侧 `webui_py/workflows.py::update_workflow` 只做:`name` 非空、节点 id 唯一、连接端点存在于节点集合、节点类型属于白名单、`node_format_error`(字段归属)、至少一个 `output`、`input/output` 节点的 `workflowPorts` 是 list、workflow 节点引用在元数据中、tool 引用已注册且参数与 schema 一致、llm 模型 id 有效。

**后果**

管理页可以直接保存以下任一图,而运行时立即抛异常(并因 F-02 静默):

- 没有 `input` 节点,或有两个 `input` 节点;
- `router` 的 `branches: []`;
- `construct_content` 的 `dataInputPorts` 与 `append_items` 不匹配(运行时 `item["port_id"]` 会 `KeyError`);
- 控制端口悬空(运行时 `next_successor` 抛 `workflow successor is not connected`)等。

**建议**

把 `agent/workflow_validator.py` 抽成不依赖 MongoDB 的纯函数模块,由 `webui_py` 直接复用,而不是在两处各写一套规则。

### H-05 存在两套互为分叉的连接校验实现,且保存时会静默丢弃连接

**证据链**

- 执行侧:`agent/workflow_contract.py::is_valid_connection` + `filter_connections`,被 `workflow_parser.py` 与 `workflow_validator.py` 共用。
- 保存侧:`webui_py/workflows.py::filter_invalid_connections`(约 60 行)与 `synchronize_metadata_ports` 内嵌的过滤,是**独立重写的第二套规则**。
- 两套规则并不等价。例如对 `llm` 节点的 `output` 端口:
  - 执行侧 `is_valid_connection` 只检查 `from_port in source_outputs`,末尾仅额外约束 `llm.tool_calls` 必须是 `list-content`;因此 `llm.output --message--> …` 会被**接受**;
  - 保存侧 `source_type()` 对 `node_type in {"llm","tool"} and from_port == "output"` 一律返回 `"content"`,并要求 `source_type() == connection_type == target_type()`,因此同一条连接会被**判定无效并删除**。
- `filter_invalid_connections` 的语义是"过滤",返回值直接被写回文档(`values["connections"] = synchronized_connections`),即**静默丢弃**而不是报错。

**后果**

- 用户在编辑器里画的连接,保存后可能无声消失,且没有提示。
- 两套规则会持续分叉,任一侧改动都不会被另一侧感知。

**建议**

共用同一份校验规则(同 H-04);并把"删除了 N 条连接"作为响应字段返回给前端提示。

### H-06 `active` 与 `tool_excute` 是死代码,连带文档能力与历史投影失效

**证据链**

- `agent/task_worker.py::handle_map` 注册了 `qq / terminal / tool_excute / tool_return / active / response / rpc_review / rpc_apply / workflow` 九种事件。
- 检索全仓库的生产者:
  - `"active"` 事件只在 `active()` 自身内部被 `insert_to_queue` 产生(`if tool_calls: insert_to_queue(..., {"event_type": "active", ...})`),**没有任何外部生产者**;
  - `"tool_excute"` 在 `handle_map` 中注册,但**全仓库无任何一处发布该事件**(运行时 `workflow_tool` / `workflow_tool_call` 是直接同步调用 `execute_tool`,不走事件);
  - `"application"` 的唯一潜在生产者位于 `qqbot_consumer/tools.py`,但该处代码被整段注释掉。
- 与此同时,下列逻辑**只存在于 `active()` 内部**:
  - `system_prompt` 的占位符替换(`{{TARGET_USER_ID}}`、`{{BOT_ID}}`、`{{SYSTEM_DOCUMENTS_PROMPT}}`);
  - 从历史投影出 `<Command>` / `<tool>` / `<response>` / `<application>` 上下文;
  - `settings['max_context_count']` 驱动的 `get_recent_history(...)` 条数控制;
  - `system_documents_prompt()` 注入(即"钉住文档自动进上下文"这一能力)。

**后果**

- `agent/settings.json` 中的 `system_prompt`、`max_context_count`,以及"钉住文档自动进入系统提示词"这三个特性在当前运行时**全部不生效**;数据库中 `settings` 集合的 `system_prompt` 亦然。
- 运行时的 LLM 上下文完全由 LLM 节点的 `prompt` 参数 + `message-in-*` 端口决定,与上文机制无关。
- 事件流前端 `webui_py/static/render.js::eventPreview` 仍为 `active` 保留特判(`if (item.event?.event_type === 'active') return '请求 LLM 处理'`),属于对已死事件的适配。
- `active()` 内还有一处脆弱点:`int(settings.get('max_context_count'))` 在设置缺失键时会 `TypeError`;且历史投影的 `for i in h` 循环中,`task_content` 变量在 `payload` 为 None 时存在未定义风险。

**建议**

明确取舍:(a) 删除 `active`/`tool_excute` 分支并同步删除 `webui_py/static/render.js` 的 `active` 特判,同时把 `system_documents_prompt()` 注入能力迁移到 LLM 节点(例如新增"注入文档索引"开关);或 (b) 若仍要保留旧链,则应补上生产者并修正 `int(...)` 的类型问题。

### H-07 未知 `event_type` 触发 `TypeError`,缺少可诊断信息

**证据链**

```python
record_history(e)
handler = handle_map.get(e['event_type'])
handler(e)
```

`handle_map.get()` 对未知类型返回 `None`,随后无条件调用。事件类型缺失时 `e['event_type']` 本身先抛 `KeyError`。

**后果**

一条来自任意入口的畸形事件只会留下一行 `TypeError: 'NoneType' object is not callable` 堆栈(经 F-02 的兜底 except 打印),事件已入库但无解释。排查时需要人工比对事件类型拼写。

**建议**

```python
handler = handle_map.get(e.get("event_type"))
if handler is None:
    record_history({"event_type": "error", "payload": {...未知类型与原始事件摘要...}})
    return
```

### H-08 WebUI 终端提交使用 `RPUSH`,会插队到所有待处理事件之前

**证据链**

- `webui_py/events.py::submit_terminal` 直接操作 Redis(未复用 `queue_client`):
  ```python
  redis_client.rpush(queue_name, json.dumps(event, ensure_ascii=False, separators=(",", ":")))
  ```
- worker 消费端是 `agent/queue_client.py::pop_from_queue` → `client.brpop(...)`,即**从尾部取**。
- 其余入队路径统一使用 `lpush`(`agent/queue_client.py::publish_to_queue`、`qqbot/listener.py`、`qqbot_consumer`)。

**后果**

`RPUSH` + `BRPOP` = 立刻被下一个 `BRPOP` 取出,即 WebUI 终端消息**优先于队列中所有已排队的 QQ 消息**被处理;而 `qq` 事件则老实排队。同一类"外部入口事件"在两条路径上获得不同优先级,且这个行为没有在代码中显式表达(靠 `rpush` 与 `brpop` 的隐含配对)。

**建议**

统一通过 `queue_client` 入队;若"终端需要即时响应"是刻意的,应把它做成显式的优先级参数(例如独立的优先级 List),而不是依赖方向约定。

## 3. 中危问题(Medium)

### M-01 每个 Workflow 事件都新建 Mongo 连接并全量读定义

`agent/task_worker.py::read_active_workflow_id()` 内部 `with MongoClient(**mongo_kwargs) as client:`;`agent/workflow_parser.py::_read_workflow()` 同样 `with MongoClient(**mongo_kwargs) as client:`。二者都在 `workflow()` 里被调用一次;`workflow_workflow` 节点还会为每个子 Workflow 再调用一次 `_read_workflow`。

对比:`agent/history_repository.py` 已用模块级 `_client/_collection` 做了单例复用。同一个仓库内两种做法并存。

**后果**:N 个节点事件 = 至少 2N 次 TCP+TLS 建连与鉴权、N 次全量文档读。工作流定义几乎不变,却每次都重新拉取。

**建议**:复用 `history_repository` 同款的模块级 client;对 workflow 定义加进程内 TTL 缓存(例如 5 秒),以 `updated_at` 作为失效依据。

### M-02 事件全量落库,缺少体积控制

`handle_task()` 中 `record_history(e)` 对所有事件无条件执行;`history_repository.record_history` 把整个 `e` 展开写入(`document = {**e, "created_at": ...}`)。事件来自 Redis 队列的原始 JSON,payload 内容不受限。WebUI 侧对事件的写操作有 256 KB 上限(`events.py::update_event` 中的 `MAX_EVENT_BODY_BYTES`),但**入库与队列写入路径没有等量限制**。

**建议**:入库前对超长 payload 做摘要化或截断,并记录原始长度。

### M-03 `workflow_tool` 与 `workflow_tool_call` 的错误处理策略相反

- `workflow_tool`:
  ```python
  result = execute_tool(node["id"], node_argument(node, "tool"), arguments)
  ```
  无 `try/except`,工具异常直接冒泡 → F-02 静默。
- `workflow_tool_call`:
  ```python
  try:
      arguments = json.loads(raw_arguments)
      ...
      result = execute_tool(tool_call_id, tool_name, arguments)
  except (json.JSONDecodeError, TypeError, ValueError) as error:
      result = f"Error: tool arguments JSON parse failed: {error}"
  except Exception as error:
      result = f"Error: {error}"
  ```
  异常被转换成字符串结果继续流转。

**后果**:同样是"工具失败",一个让整条链静默死掉,另一个把错误文本喂给下游 LLM。行为不可预期。

### M-04 `workflow_tool_call` 的外层 JSON 解析在 `try` 之外

```python
tool_call = json.loads(raw_tool_call)          # ← 不在 try 内
if not isinstance(tool_call, dict): raise ValueError(...)
...
try:
    arguments = json.loads(raw_arguments)      # ← 在 try 内
```

同一个函数里,参数 JSON 解析失败会被优雅处理,而**外层 tool_call JSON 解析失败会直接冒泡**成 F-02 静默中断。这是 LLM 输出质量最容易出问题的一环。

### M-05 `router` 分支名严格精确匹配且无默认分支

`workflow_router` 用输入的原始值直接拼后继键:

```python
has_key, key = read_workflow_input(node, "content-in")
if not has_key: raise ValueError(...)
return next_successor(node, f"branch-{key}")
```

`parse_workflow::_successor_key` 也是按 `branch['name']` 精确匹配(`return f"branch-{branch['name']}"`)。而 `workflow_validator` 对 `branches` 只校验"非空、id/name 各自唯一",不要求存在兜底分支。

**后果**:LLM 输出大小写差异、首尾空格或任何不在分支名集合中的值,都会让 `next_successor` 抛 `ValueError`,链路静默中断(F-02)。缺少"默认分支"概念。

**建议**:匹配前做 `strip()`/大小写归一;或在节点契约中强制一条默认分支,未命中时走默认。

### M-06 入口端口名不匹配时静默丢数据

`workflow()` 用 `e['payload'].get(port['name'])` 取值,而两个入口构造的 payload 是固定键名:

- `task_worker.qq()` → `{"content": raw_message, "source": "qq"}`
- `task_worker.terminal()` → `{"content": ..., "source": "terminal"}`

若画布 Input 节点的端口名不是 `content`/`source`,`.get()` 返回 `None`,写入槽位后 `read_workflow_input` 判为"无值"(与 F-04 同一机制),下游 LLM 节点的 `message-in-*` 全部落空。

**后果**:LLM 节点最终收到的 `messages` 可能只有 `prompt` 对应的一条 system 消息,甚至为空列表 → API 报错 → F-02 静默。整个过程没有任何提示。

**建议**:入口侧显式校验端口名并记录缺失;`workflow_llm` 在 `messages` 为空时抛出带节点 id 的明确错误。

### M-07 `agent/tools/tool.py` 在 import 时清空工具注册表

```python
registered_tools = []
tool_handlers = {}
redis_reset_tools()          # ← 模块级副作用,DELETE aagent:tools
```

`redis_reset_tools()` 会删除 Redis 中的 `AGENT_TOOLS_KEY` 哈希。

**后果**:

- 任何 `import tools.tool` 的进程(包括一次性脚本、测试、`debug_workflow.py` 若间接引入)都会**清空线上工具注册表**。
- agent 重启期间(清空 → 重新 `@tool` 注册之间)存在窗口,此时管理页 `/api/tools` 与编辑器工具列表为空。
- 编辑器若在此窗口打开,用户看到"零工具";管理页此时保存 tool 节点会被拒绝。

**建议**:把 reset 改为显式的启动步骤(在 `main()` 中调用),或改成"注册后以 `HSET` 覆盖 + 用版本键标记本轮注册"的幂等方案。

### M-08 启动时用本地文件覆盖 Redis 设置

```python
def initialize_settings():
    set_settings(read_settings_file())     # 无条件 SET aagent:settings
```

`main()` 开头调用。`agent/settings.json` 是随仓库分发的种子文件(且不参与镜像排除,见 M-16)。

**后果**:每次 agent 重启,任何通过其他途径写入 Redis 的设置都被本地文件覆盖,且无审计。

**建议**:改为"仅当 Redis 中不存在该键时"写入(`SET ... NX`),或改为显式的一次性迁移命令。

### M-09 `agent/tools/documents.py` 的性能与健壮性问题

- `system_documents_prompt()` 每次调用都执行 `list_documents()` → `documents_collection.find()` **全表扫描**(无投影),再把每个 `pinned` 文档的**完整内容**拼进提示词。当前它只在(已死的)`active()` 中被调用;若迁移到 LLM 节点,需先解决这一点。
- `query_document_by_id(doc_id)` 与 `document_wrapper(doc_id)` 都是 `i = ...find_one(...)` 后直接 `i['title']`,**未判空**。文档不存在时抛 `TypeError: 'NoneType' object is not subscriptable`。
- `list_documents()` 无投影,返回全部 `content`,但调用方只用 `title`/`pinned`。
- `append_to_document` / `rewrite_document` 中 `return_document=return_final` 传入的是 **`bool`** 而非 `pymongo.ReturnDocument` 枚举。当前依赖 `ReturnDocument.BEFORE == 0` / `AFTER == 1` 与 `bool` 的整型等价性"碰巧可用";此外 `return_final=False` 时会 `return str(res)`,而 `res` 此时是**更新前的整份文档**(含 content),被塞进工具的返回值并最终进入 LLM 上下文。
- `query_document_by_name` 未对同名多文档做数量提示,直接把全部命中文档的完整 `content` 拼接返回。

**建议**:补空值判断;给列表类查询加投影;"全表 + 全文"改为按需检索。

### M-10 `get_recent_history` 的可变默认参数

```python
def get_recent_history(limit: int = 10, query: dict = {}, event_type: str | None = None) -> list[dict]:
    if event_type is not None:
        query["event_type"] = event_type
```

`query={}` 是模块级共享对象,`query["event_type"] = event_type` 会**污染后续所有调用**。当前唯一调用方 `active()` 不传该参数,属潜伏缺陷。

**建议**:`query: dict | None = None` 后在函数内拷贝。

### M-11 请求体守卫只依赖 `content-length`

`webui_py/main.py::request_body_guard` 只读取 `request.headers.get("content-length")` 并与上限比较;请求头缺失或使用 `Transfer-Encoding: chunked` 时不受限。

**建议**:叠加对实际读取字节数的累计上限(或依赖反向代理的 `client_max_body_size`)。

### M-12 编辑器会把 LLM 节点的 `content-in-N` 端口静默改写为 `message-in-N`

`workflow_editor/static/workflow/domain/serialization.js::normalizeNode` 中:

```js
const declaredCount = Array.isArray(node.dataInputPorts)
  ? node.dataInputPorts.filter((portId) => typeof portId === 'string' && /^(?:content|message)-in-\d+$/.test(portId)).length
  : 1;
normalized.dataInputPorts = Array.from({ length: Math.min(20, Math.max(1, declaredCount)) }, (_, index) => `message-in-${index}`);
```

正则**同时接受** `content-in-*` 与 `message-in-*`,但产出**永远**是 `message-in-*`。

**后果**:任何含 `content-in-N` 的历史/外部 JSON,在载入编辑器时端口名与端口类型(`portsForNode` 中 llm 的输入端口 type 固定为 `'message'`)都会被改变;原指向 `content-in-N` 的连接在 `filterValidConnections` 中被判定无效并丢弃,数据静默丢失。

**建议**:要么保持原名(仅做数量裁剪),要么在改写时给出提示。

### M-13 编辑器与服务端各持一份节点契约常量

**后果**:新增节点类型或字段时需同步改四处;漏改任何一处会产生"编辑器能画、管理页拒绝"或"管理页能存、运行时拒绝"的不一致。

### M-14 编辑器通过 URL 查询串传递整份 Workflow JSON

`workflow_editor/static/workflow.js`:

- `qqbot_consumer/llm.py::send_messages` 中 `print(resp.json())`。
- `agent/tools/bilibili.py::asr` 中 `print(response.json())`。

**后果**:容器日志被完整响应体(含 reasoning 与 tool_calls)淹没,敏感内容进入日志。

### L-04 `workflow_editor` 健康检查不探测依赖

```python
@app.get("/api/health")
def health():
    return {"status": "ok"}
```

无条件返回 ok。Redis/Mongo 不可用时编辑器页面仍显示在线,只有具体资源读取失败。对比 `webui_py/main.py::health` 会 `redis_client.ping()` 并在失败时返回 503。

### L-05 死代码:多个未使用的函数与参数

- `qqbot_consumer/llm.py::chat_with_llama_cpp(messages)` 只接收 `messages`,函数体却调用 `send_messages(messages, "http://127.0.0.1:8080", "", "")` 并直接截断——无调用方。
- `agent/task_worker.py` 的 `handler` 集合里 `tool_return`、`response`、`rpc_review` 三个处理器均为 `pass`。
- `agent/workflow_contract.py::normalize_node_arguments` 返回的字典中,`NODE_BASE_FIELDS` 里的 `arguments` 字段本身被排除在外(`if key in NODE_BASE_FIELDS or key in NODE_SHARED_FIELDS` 会把已展开的 `arguments` 键重新收进来),`parse_workflow` 之后又显式 `pop("x")`/`pop("y")`,存在冗余。

### L-06 `settings.example.json` 与真实的提示词投影不符

`agent/settings.example.json` 的 `system_prompt` 描述的是 `<QQ event='msg' type='private' ...>` 形式的注入,而 `task_worker.py::active()` 实际生成的是 `<Command source='qq'>`、`<tool>`、`<response>`、`<application>`。模板还引用 `{{BOT_ID}}`,而实际替换列表是 `{{TARGET_USER_ID}}`、`{{BOT_ID}}`、`{{SYSTEM_DOCUMENTS_PROMPT}}`(此项在示例中用的是 `{{SYSTEM_DOCUMENTS_PROMPT}}` 之外的写法需逐一核对)。`max_context_count` 示例为 `"12"`,实际 `settings.json` 为 `"16"`。

**后果**:按模板自建 `settings.json` 的用户会得到与运行时投影不匹配的提示词。

### L-07 前端事件指纹存在碰撞可能

`webui_py/events.py::event_fingerprint` 是自实现的 FNV-1a 变体并按 base36 输出。该指纹被用于:
- 队列事件的乐观并发校验(`delete_event`/`update_event` 中比对 `fingerprint`);
- 前端行的 React 风格复用键(`id = f"pending-{fingerprint}-{n}"`)。

哈希碰撞会让不同事件被视作同一项,导致删除/更新作用于错误目标。概率极低,但这里并不需要哈希——直接使用 `json.dumps(..., sort_keys=True)` 的完整串即可。

### L-08 `webui_py/workflows.py::rename_workflow` 的级联更新会刷新引用方的 `updated_at`

级联 `update_many` 的 `$set` 中包含 `"updated_at": datetime.now(timezone.utc)`。而被引用的 Workflow 改名时,引用方**内容并未变化**,却会因此被顶到管理列表最前。属于轻微的语义污染。

### L-09 重命名级联使用单条 `update_many` 承载两个 `arrayFilters`

```python
workflows.update_many(
    {"$or": [
        {"workflow_nodes.name": previous_name},
        {"nodes": {"$elemMatch": {"type": "workflow", "arguments.workflow_name": previous_name}}},
    ]},
    {"$set": {
        "workflow_nodes.$[reference].name": name,
        "nodes.$[node].arguments.workflow_name": name,
        "updated_at": datetime.now(timezone.utc),
    }},
    array_filters=[
        {"reference.name": previous_name},
        {"node.type": "workflow", "node.arguments.workflow_name": previous_name},
    ],
)
```

同一文档可能只匹配 `nodes` 而 `workflow_nodes` 为空/缺失(或反之)。此时其中一个标识符无匹配元素的写入语义需要在目标 MongoDB 版本上实测确认(可能报错,也可能被忽略)。**未实测**,故列为低危。

另:主文档改名(`find_one_and_update`)与级联更新**不在同一事务**。级联抛 `PyMongoError` 时接口返回 503,但主文档已改名,引用方仍指向旧名,形成悬空引用。

### L-10 校验规则集在四处实现,且 `input` 节点数量上限缺失

`update_workflow` 校验了"至少一个 output",但**未校验** `input` 节点数量(恰好为 1)。执行侧 `validate_workflow` 有这个约束。这属于 M-13/H-04 的具体表现,单列以便定位:管理页可保存 0 个或 2 个 `input` 节点的 Workflow。

### L-11 `openai_llm_api` 的 `extra={}` 可变默认参数

`agent/llm.py::openai_llm_api(messages, model, url, key, tools=registered_tools, extra={})`。当前函数体只做 `**extra` 展开,未修改该字典,故无实际影响;但同类模式已在 M-10 造成真实缺陷。

## 5. 跨领域结构性问题

### X-01 大量复制粘贴的服务副本

| 组件 | 副本数 | 位置 |
| --- | --- | --- |
| `queue_client.py` | 3(+1 内联) | `agent/`、`qqbot/`、`qqbot_consumer/`;`webui_py/events.py` 内联直接操作 Redis |
| `llm.py` | 2 | `agent/llm.py`、`qqbot_consumer/llm.py` |
| `history_repository.py` | 2 | `agent/`、`qqbot_consumer/` |

| 节点契约常量 | 4 | 见 M-13 |

**已产生的实际分歧**:H-01(`lpush`+`blpop` vs `lpush`+`brpop`)、H-03(webui 回显密钥 / editor 不回显)、M-22(一方有 socket 超时一方没有)。

### X-02 事件格式约定不统一

- `qq`/`terminal`/`workflow` 事件使用 `{"event_type": ..., "payload": {...}}`;
- `rpc_review` 的重发布把业务字段放在**顶层**(F-03);
- 部分事件带 `"time"`(`events.py::submit_terminal` 生成),部分不带;
- `response` 事件的 payload 有时含 `context`(完整 messages)、有时只含 `content`。

没有单一的事件构造/校验入口,格式靠约定维持。

### X-03 `validate_workflow` 对控制流环不做限制(需明确为有意行为)

`workflow_validator.py` 校验控制端口连通性与输出唯一后继,但不做环检测;`run_workflow_map` 是 `while current_id != WORKFLOW_END` 的循环,环会导致**无限循环**,并且每轮都调用 `discover` 之外的 LLM/工具时开销巨大。

若允许环(例如 `foreach` 的 `loop-in`/`loop-out` 就是必需的环),应显式记录为设计决策,并考虑加一个迭代上限保护。
