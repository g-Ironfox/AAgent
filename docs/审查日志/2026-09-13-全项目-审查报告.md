## 1. 结论

有条件通过。Workflow 运行时的节点契约、控制/数据流语义与 `workflow_parser.py`/`workflow_validator.py` 契约自洽,编辑器导出 → 管理页上传的字段链与 `WorkflowRequest(extra="forbid")` 严格吻合,既有 WebUI 防御面保持。但发现 3 项 P1:运行期节点失败无事件反馈(R1)、`rpc_apply`→`rpc_review` 子 Agent 回发链路不闭环(R2)、核心文档 00-08 仍整体描述 `active` 旧链且零处提及 `workflow_*` 事件(M1)。另有 8 项 P2、8 项 P3 与 2 项 P4。

## 2. 已核验

1. **Workflow 运行时数据/控制流与契约同源**:逐节点核对 `task_worker.py` 的 `workflow_*` 分支与 `workflow_contract.py`:input 按 `workflow:<name>` 端口注入、router 走 `branches[*].successor`、foreach `loop-in`/`loop-out` 回环、workflow 调用节点 `workflow:<name>` 双向端口与 `_workflow_call_stack` 递归防护、`workflow_output` 的父子回填均与 `data_ports_for_node`/`control_ports_for_node` 一致;
2. **边界端口命名同源**:`boundaryPorts()`(编辑器)、`boundary_ports()`(agent)、`synchronize_metadata_ports()`(webui)三处一致产出 `{id: workflow:<name>, name, type}`;`agent/test_workflow_node.py` 的断言仍与实现匹配;
3. **队列三语义在 workflow 链上成立**:节点分发走 `publish`(LPUSH 普通排队)、BRPOP 尾部消费,工作流链与外部新事件之间保持到达顺序 FIFO;`insert`(RPUSH)语义未被新代码破坏;
4. **上传链路字段契约**:`webui_py/static/workflows.js` 上传/覆盖先 `PUT /metadata` 再 `PUT /api/workflows/{id}`,载荷剥离 `workflow_nodes` 与节点级 `workflow_id`,与 `WorkflowRequest(extra="forbid")` 吻合;`resolveWorkflowReferences` 兼容 `name`/`workflow_name`/`workflow_id` 三种引用形态;
5. **WebUI 后端防御面保持**:事件删除/编辑的 Lua 原子替换与指纹校验、终端 16KB/文档 1MB/Workflow 512KB 请求体限制、`{"error": ...}` 错误契约均保持 2026-08 已核验水平;
6. **qqbot 队列入队/出队方向配对**:`listener.py` LPUSH 入 `subagent:qq:tasks`,`qqbot_consumer` BLPOP 消费(FIFO),再 LPUSH 转发主队列由主 worker BRPOP 消费;A11 所述方向错误的旧 `pop_from_queue` 仍是死代码,不影响运行;
7. **compose 编排**:健康检查、`service_healthy` 门控、`data/` 持久化、正式配置不暴露 Redis/Mongo 端口与文档一致;`docker-compose.dev.yml` 的 6379/27015 暴露与 docs/04 §1.1 一致;
8. **旧问题抽查**:A2(`command.py` 死代码)、A5(Redis 客户端每次新建)、A14(`inputing` 事件仍入库)、A22(`query_document_by_id` 缺 None 检查)、W11(接口无鉴权)对照源码仍成立,本轮不重复登记。

## 3. 问题清单

### P1

| # | 问题 | 说明与建议 |
| --- | --- | --- |
| R1 | Workflow 节点失败静默中断 | `task_worker.py` 的 `workflow()`/`workflow_*` 内任何异常(`validate_workflow` 失败、递归调用、`foreach` 非列表、tool_call 非法等)冒泡到 `main()` 兜底 `except`,仅 print + sleep(2);事件虽已入库,但不会产生任何失败/`response` 事件,也没有出错节点信息,用户侧表现为"发了没反应"。建议在入口与分发处捕获异常,落一条含节点 id 的失败事件并写回 `response` 让终端可见 |
| R2 | 子 Agent 回发链路不闭环 | `qqbot_consumer.send_group_message()` → 主队列 `rpc_apply` → `task_worker.rpc_apply()` 重新发布 `rpc_review`;但 `rpc_review` 处理器是 `pass`,且重发布事件把 `subagent_name`/`tool_name`/`tool_arguments` 放在顶层而非 `payload`,不符合事件格式约定。结果是 `qqbot_consumer` 群内 @ 路径(LLM 生成内容后请求发送)永远发不出消息。建议补 `rpc_review` 的审批/执行逻辑并统一 payload 结构,或删除该链路并明确群消息策略 |
| M1 | 核心文档 00-08 与运行时脱节 | 代码已改为 `qq`/`terminal` → `workflow` 事件驱动,`active` 分支仅剩自产自销的循环(`active` 无外部生产者);但 00/01/02/03/05/06/07/08 仍以 `active` 为 LLM 唯一入口描述状态机与队列语义,且 00-08 全文零处提及 `workflow_*` 事件。持续漂移会直接误导后续开发(例如按文档去改"active 分支")。建议优先修订 02/03/06 事件表与模块职责、01 架构图,再回落 00/05/07/08 |

### P2

| # | 问题 | 说明与建议 |
| --- | --- | --- |
| W1 | 保存面校验弱于执行面 | `PUT /api/workflows/{id}` 未校验"恰好一个 input 节点、router 分支非空、construct_content/construct_list 结构、控制端口连通性"等 `agent/workflow_validator.py` 规则,API 可保存执行期必然报错的图(随后触发 R1 静默中断)。建议把 agent 校验抽为共享模块由 webui 复用,或保守对齐关键规则 |
| W2 | 重命名级联的 arrayFilters 双路径 | `PATCH` 与 `PUT` 的级联更新用一条 `update_many` 同时更新 `workflow_nodes.$[reference].name` 与 `nodes.$[node].workflow_name`;对只匹配 `nodes.$elemMatch` 而 `workflow_nodes` 为空/缺失的文档存在写错误风险(待实测),且级联与主更新无事务,中途失败返回 503 时主文档已改名、引用方未更新。建议拆两条各自带条件与 arrayFilter 的更新,并考虑事务 |

| M2 | docs/13 解析器契约过期 | 文档写查询条件 `{"key": workflow_key}`,实际按 `name` 查询(或 `_id`),且 webui 启动迁移已 `$unset key`;解析结果新增的 `workflowPorts`/`workflow_name`/`branches[*].successor`/`_workflow_call_stack` 等运行时字段未覆盖;CLI 示例应传 Workflow 名称。建议重写 §1、§3 与 CLI 示例 |
